## 1. 목표와 성공 기준

오목을 네 번째 게임으로 붙인다. 2인·숨길 정보 없음·판정은 5목 검사뿐이라 지금까지 중 가장 단순하다.
그래서 이 게임의 쇼케이스 가치는 **"포트를 한 줄도 안 바꾸고 붙는다"** 를 실증하는 데 있다(스컬킹은 `desert` 3치,
원카드는 엔진 타이머 1건이 필요했다). 동시에 요트 가정으로만 남아 있던 **"비공개 뷰 없음"(`privateView` = empty)을 처음
실제로 쓰는 게임**이다.

| # | 기준 | 확인 방법 |
| --- | --- | --- |
| 1 | 인프라에 게임 이름 분기 0줄. 포트 변경 0건(봇 난이도 방 설정을 고르면 1건 — §3.3) | `grep -rni omok server/src/main/java/com/mirboard/infra` → 0건 |
| 2 | 무작위 착수 시뮬레이션 10,000판 전부 종료, 매 전이 뒤 불변식(돌 수 = 수 번호, 흑백 교대, 흑 돌이 금수 자리에 없음) | 시뮬레이션 테스트 + 불변식 검사기 |
| 3 | 금수 판정 고정 국면 30개 이상 통과(거짓 33·한 줄 44·5목과 33 동시 = 승 포함) | `ForbiddenMovesTest` |
| 4 | 봇 3단계가 서로 확실히 갈리고(위 단계 승률 ≥ 0.8), 한 수 계산이 p99 150ms 이내 | 봇 강도·시간 예산 테스트(Docker 불필요) |

## 2. 룰 (v1 기준선)

### 2.1 룰셋 선택지

| 안 | 내용 | 장점 | 단점 |
| --- | --- | --- | --- |
| **A. 렌주식 금수** *(추천)* | 흑만 33·44·장목(6목 이상) 금지. 흑은 정확히 5목만 승리, 백은 5목 이상 승리 | 국제 표준(렌주)이라 근거가 분명하다. 흑 선착 이점을 크게 줄인다. 금수는 서버가 판정하고 화면에 ✕ 로 보여 주니 사용자가 외울 필요가 없다 | 금수 판정(특히 거짓 33)을 정확히 구현해야 한다 — 테스트 국면으로 고정 |
| B. 삼삼만 금지(흑만) | 한국 동네 오목 감각. 장목·44 는 허용 | 설명이 짧다 | 표준 근거가 약하다(집집마다 다름). 44 허용이라 흑 이점이 여전히 크다 |
| C. 자유 오목 | 금수 없음, 5목 이상이면 누구든 승리 | 구현이 가장 쉽다 | 15×15 자유 오목은 흑 필승이 알려져 있다 — 실력이 비슷하면 흑이 크게 유리 |
| D. 방장이 고르기 | A·C 를 방 설정으로(`RoomOption`) | 취향을 다 받는다 | 엔진이 방 설정 값을 받아야 해 포트 확장이 필요하다(§3.3) — v1 범위를 넘는다 |

추천은 **A 고정**이다. 엔진은 금수 검사를 끄는 스위치만 있으면 C 도 되므로, 나중에 D 로 넓히는 비용은 방 옵션 배선뿐이다.
렌주의 정식 개막 규칙(스왑·5수 2개 제시 등)은 넣지 않는다 — 친구끼리 하는 판에 과하다. **첫 수는 자유**(천원 고정 안 함)로 둔다.

### 2.3 금수 판정 세부 (렌주 정의를 그대로)

`rules-omok.md` 에 정의와 그림 국면을 함께 싣는다. 구현의 기준:

1. **5**: 놓은 돌을 지나는 한 방향에서 같은 색이 정확히 5개 연속.
2. **장목**: 6개 이상 연속. 흑에게만 금수, 백에게는 승리.
3. **4**: 한 수만 더 두면 그 방향에서 정확히 5 가 되는 모양. 그 "한 수" 자리가 둘이면 열린 4(막을 수 없음), 하나면 막힌 4.
   **한 줄 44**(예: `●●●_●_●●●` 에서 가운데) 도 4 두 개로 센다.
4. **열린 3(진짜 3)**: 한 수 더 두면 열린 4 가 되는 3 — 단, **그 한 수 자리가 흑에게 금수가 아니어야 한다**(거짓 33 제외).
   이 조건 때문에 판정이 재귀다. 재귀는 같은 줄 몇 칸 안에서만 일어나 깊이가 작고, 메모해 두면 비용이 무시된다.
5. 우선순위: 5 > (장목·44·33 금수). 즉 5목을 만드는 수는 다른 조건과 무관하게 둘 수 있다.

### 2.4 흑백 정하기 · 시간 초과

**흑백** — 선택지(§10 Q2):

| 안 | 내용 |
| --- | --- |
| **무작위** *(추천)* | 매치 시작 때 서버가 추첨(`SecureRandom`, 라운드 스타터). 좌석 0/1 과 무관 |
| 진 사람이 흑(교대) | 친구끼리 연속으로 할 때 공평. 대기실 복귀(D-153) 뒤에도 "지난 판 결과"를 방에 남겨야 한다 — 칩(`room:{id}:chips`)처럼 방 단위 Redis 값이 하나 더 생긴다 |
| 방장이 흑 | 단순하지만 불공평 |

무작위로 시작하고, 친구 판의 교대는 쓰임을 본 뒤 후속으로 둔다.

**시간 초과** — 선택지(§10 Q3):

| 안 | 내용 |
| --- | --- |
| **자동 한 수 + 2번 연속이면 시간패** *(추천)* | 시간이 다 되면 서버가 결정적으로 한 수 둔다(마지막 수에서 가장 가까운 합법 빈칸, 같으면 y·x 순). 같은 사람이 **연속 2번** 시간 초과면 그 자리에서 진다. 한 번 놓친 사람은 살리고, 자리를 비운 사람은 빨리 정리한다 |
| 바로 시간패 | 온라인 오목의 흔한 방식. 휴대폰에서 잠깐 앱을 바꾸면 진다 |
| 자동 한 수만 | 판이 끝나지 않고 늘어진다(상대가 사실상 혼자 둔다) |

턴 제한은 **기본 30초**, 선택지 **끔·15·30·60**(`turnSecondsChoices`). 끔이면 자리를 비운 사람을 남은 사람이 기다리거나 나가야 하는데,
나가면 나간 쪽이 탈주패라 기본을 켠 상태로 둔다(원카드 D-130 과 같은 이유). 끊긴 상대는 방장 [내보내기](D-162)로 정리된다.

### 3.2 2인 고정·숨길 정보 없음이 주는 영향

- **상태 은닉 규칙이 할 일이 없다.** 비공개 이벤트가 `ERROR` 하나뿐이고 손패가 없다. 그래도 "공개 뷰에 숨길 것이 섞이지 않는다"는
  직렬화 테스트는 둔다 — 지킬 것은 **봇의 내부 정보**(탐색 결과·평가 점수)가 공개 뷰에 안 실리는 것 하나다.
- **관전자가 전부 본다.** 관전은 공개 토픽만 받으므로 그대로 된다. 다만 사람끼리 판에서 관전자가 훈수를 채팅으로 줄 수 있다 —
  막을 수단이 없고 친구 판이라 v1 은 허용(§9).
- **resync 의 `privateHand` 가 처음으로 `null` 인 게임**이다. 서버(`RoomController.resync` 는 `.orElse(null)`)는 이미 준비돼 있고,
  클라 공통 훅·`RoomEventSink` 가 `null` 을 받는 경로를 S3·S4 테스트로 처음 고정한다.
- **2인 고정**: D-143·D-174 뒤로 방 만들기에 인원 선택이 없다(정원 = 게임 최대 = 2). 둘이 모이면 방장 "2명으로 시작".
  봇은 [빈자리 봇으로 채우기]로 1명(시드 봇 8명이라 풀 문제 없음).
- **좌석 배치(D-132)**: 2인이라 `tableLayout` 이 필요 없다 — 상대는 판 위, 나는 판 아래 고정. 관전자는 흑이 아래.
- **탈주 3치 중 `MATCH_CONTINUES` 를 안 쓴다**(티츄와 같다). 대기실 복귀(D-153)·봇 방 정리(D-174)는 인프라 그대로.

### 3.3 봇 난이도를 어떻게 고르나 — 포트 변경 0 이냐 1 이냐

난이도는 엔진(봇 정책)이 알아야 하는데, 지금 엔진에 들어오는 방 설정은 `GameContext(roomId, playerIds, targetScore, stake,
botSeats)` 뿐이다. 원카드 버튼 크기(`RACE_BUTTON_SIZE`)는 화면만 바꿔서 엔진까지 갈 필요가 없었다.

| 안 | 내용 | 포트 |
| --- | --- | --- |
| A. 한 단계(보통)만 *(v1 최소)* | 난이도 선택 없음. 3단계 정책은 만들어 두고 강도 평가에만 쓴다 | **변경 0** — 쇼케이스 문구 "네 번째 게임은 포트 변경 0" |
| **B. 대기실 방 설정 `BOT_LEVEL`** *(추천)* | 방장이 대기실 `RoomSettingsPanel` 에서 쉬움·보통·어려움(봇이 앉은 방에서만 보임). `RoomOption` 상수 1개 + `Room` 필드 1개(원카드 버튼 크기와 같은 경로) + **`GameContext` 에 방 옵션 값 전달** | **확장 1건** — `GameContext` 에 게임 중립 `options`(`Map<RoomOption,String>`, 게임이 선언한 옵션만) |
| C. 봇 계정마다 난이도 | `bot_north` = 쉬움 … 처럼 계정에 묶음 | 변경 0 이지만 시드 데이터에 룰이 묶이고, 봇 고르기 UI 가 따로 필요 — 기각 |

B 의 확장은 오목 전용이 아니다 — 같은 시기에 기획 중인 요트 등 다른 후보도 "봇 강도"나 "룰 변형"을 방 설정으로 받으려면 같은
자리가 필요하고, §2.1 D 안(룰셋 선택)도 이 확장 위에 공짜로 얹힌다. 추천은 **B** 다(사용자 요청의 "난이도 단계"를 실제로 고를 수
있어야 의미가 있다). 고르면 `docs/game-port.md` 에 절 하나를 먼저 쓴다.

## 4. 서버 설계

### 4.1 패키지 `domain.game.omok`

원카드의 2계층(순수 룰 엔진 + 포트 어댑터)을 그대로 따른다. 괄호는 만드는 단계다.

```
omok/
  OmokGameDefinition   @Component · ID "OMOK" · 2인 · 상태는 설정(MIRBOARD_OMOK_STATUS, 기본 COMING_SOON → S5 에서 AVAILABLE) (S3)
  OmokEngine           순수 룰 엔진 — 저장소·시계 없음 (S1)
  OmokGameEngine       포트 어댑터 — 상태 저장(Redis)·로컬 발행·봇 안전망 (S3)
  board/      Point · Stone · Board(15×15, 놓기·읽기, 불변) (S1)
  rules/      LineScanner(4방향 연속 수) · WinRule(정확히 5 / 5 이상) · ForbiddenRule(33·44·장목, 재귀 3 판정) (S1)
  state/      OmokState · MatchResult · OmokStateMapper(공개 뷰) (S1)
  action/     OmokAction(sealed: Place · Resign · TimeoutPlace*) · RejectionReason · OmokActionRejectedException (S1)
  event/      OmokEvent(sealed) (S1) · OmokMatchCompleted (S3)
  invariant/  OmokInvariantChecker (S1)
  bot/        OmokBotPolicy(쉬움·보통·어려움) · PatternEvaluator · ThreatSearch(VCF) · OmokBotView (S2)
  lifecycle/  OmokRoundStarter(GameStartingEvent → 흑 추첨·빈 판 저장) (S3)
  persistence/ OmokStateStore · OmokMatchRecorder · OmokHeadToHead (S3)
```

\* `TimeoutPlace` 는 **Jackson 하위 타입으로 등록하지 않는다** — 클라 JSON 으로는 만들 수 없고, 서버의 `timeoutAction` 만 만든다.
엔진은 이것으로 "연속 시간 초과"를 센다(포트 경로: `TurnTimeoutScheduler` 가 `apply(state, seat, timeoutAction(...))`). 클라가 보내는
`Place` 는 그 좌석의 연속 시간 초과 수를 0 으로 되돌린다.

### 4.2 상태

불변 레코드. 판은 수순에서 파생할 수 있지만 매 액션 재구성을 피하려고 둘 다 둔다(저장은 수순만, 로드 때 판을 다시 만든다).

- `OmokState`: 흑 좌석(0/1) · 수순 `List<Point>`(짝수 번째 = 흑) · 차례 좌석(끝나면 −1) · 좌석별 연속 시간 초과 수 · 결과(끝나기 전 null)
- `MatchResult`: 승자 좌석(무승부면 −1) · 사유(`FIVE`·`RESIGN`·`TIMEOUT`·`DESERTED`·`BOARD_FULL`·`NO_LEGAL_MOVE`) · 승리 줄 5점(5목일 때만)
- 파생: 판(`Board`), 다음 색, 흑 차례의 금수 목록(공개 뷰·`legalActions`·검증이 같은 함수를 쓴다)

### 4.3 엔진·어댑터

- `OmokEngine.apply` — 검증(차례·범위·빈칸·금수) → 놓기 → 5목/장목 판정 → 판 가득 참 판정 → 다음 차례 · 이벤트. 시간 초과
  수 갱신. `Resign` 은 차례와 무관하게 받는다(내 차례가 아니어도 기권 가능).
- `OmokGameEngine` — 원카드 어댑터의 모양을 그대로: 상태 저장·로드, 결과가 나면 `OmokMatchCompleted` 로컬 발행(D-116)을 발행 지점에서
  `RuntimeException` 으로 감싸 진행 경로로 새지 않게(매치 기록기 계약 3 — 리스너 하나), 봇 정책 안전망(예외·null·비합법 → ERROR 후
  `timeoutAction`).

### 4.4 봇 정책 — 3단계, 무료 서버 CPU 안에서

**예산의 근거**: `BotScheduler` 는 **방 액션 락(`SET NX EX 2s`)을 쥔 채** `botAction` 을 부른다. 계산이 길면 락이 만료돼 다른 액션과
겹친다. 운영 VM 은 `shared-cpu-1x / 512MB`(무료 범위, 사양 올리기 금지). 그래서 **한 수 p99 150ms, 상한은 시간이 아니라 노드 수**로
건다 — 시간 상한은 재현성을 깨고(같은 상태 같은 수 — 포트 §5-3 원칙), 노드 상한은 결정적이다. 사람 페이스는 이미 있는 봇 지연
(`mirboard.bot.delay-millis`, 운영 700ms)이 맡는다.

공통 부품:

- **후보 수**: 기존 돌에서 거리 2 이내 빈칸(보통 20~60개). 첫 수(빈 판)는 천원(7,7).
- **패턴 평가**(`PatternEvaluator`): 칸마다 4방향으로 내 돌/상대 돌을 놓아 보고 모양 점수를 더한다 — 5 ≫ 열린 4 ≫ 막힌 4 ≈ 열린 3 ≫
  막힌 3 ≈ 열린 2. 공격 점수 + 방어 점수 × 가중.
- 흑일 때는 `legalActions` 가 이미 금수를 뺀다(봇이 금수를 두지 않는다).

| 단계 | 방법 | 사람 체감 |
| --- | --- | --- |
| 쉬움 | 1수 평가, 방어 가중 낮음. 이길 수(5)와 상대 4 막기는 항상 하지만 **열린 3 방어를 일부 놓친다** — 상위 3개 후보 중에서 상태 해시(수순)로 고른다(무작위 아님, 같은 국면 같은 수) | 처음 하는 사람이 이길 수 있다 |
| 보통 | 1수 평가 + 필수수 규칙: 내 5 → 둔다 · 상대 4 → 막는다 · 내 열린 4 → 만든다 · 상대 열린 3 → 막거나 4 로 역공 | 대충 두면 진다 |
| 어려움 | 보통 + **VCF 탐색**(연속 4 로 이기는 수순, 깊이 ≤ 12수) + 상대 VCF 확인(있으면 막는 수 우선) + 얕은 알파베타(깊이 3, 후보 상위 8). 노드 상한 30,000 | 동네 고수 수준. 렌주 정석은 모른다 |

- 강도 평가(D-119 방식, `bot/OmokBotStrengthTest`): 흑백 번갈아 각 200판 — 어려움 대 보통 ≥ 0.8, 보통 대 쉬움 ≥ 0.8, 보통 대 무작위
  ≥ 0.99. 시간: 국면 1,000개에서 어려움 p99 ≤ 150ms(로컬 측정값을 문서에 남기고, 운영 VM 은 2~3배 느리다고 보고 노드 상한을 잡는다).
- 백 봇이 흑을 금수로 유도하는 전략은 v1 범위 밖(§9).

### 4.5 기록·랭킹

- **V13**(착수 시점의 다음 번호): `omok_match_results`(room_id, finished_at, end_reason, winner_seat nullable, moves_json — 기보) +
  `omok_match_participants`(match_id, user_id, seat, color, is_win, is_draw, deserted). 스컬킹·원카드의 2테이블 구조. 기보를 남겨 두면
  나중에 "다시 보기"를 서버 변경 없이 붙일 수 있다.
- **`OmokMatchRecorder`**: `OmokMatchCompleted` 리스너. ELO 는 `EloCalculator.applyFreeForAll` 2인(승 1·패 0, 무승부는 같은 점수 → 0.5),
  탈주는 `deserted`. 봇·게스트가 끼면 ELO 미적용(`RatedMatchPolicy.eloApplies`). 비봇 참가자마다 `user_game_stats` 행(계약 2).
- 랭킹 탭·계급(D-166)·전적·상대 전적은 카탈로그 기반이라 자동으로 생긴다(`game_type = 'OMOK'`).

## 5. 이벤트·프로토콜 (STOMP)

| 방향 | type | 내용 |
| --- | --- | --- |
| 클라→서버 | `PLACE_STONE` | `x`, `y` |
| 클라→서버 | `RESIGN` | — |
| 공개 | `MATCH_STARTED` | 타입만 정의, 발행하지 않는다 — 시작 상태는 resync 로(원카드 선례) |
| 공개 | `STONE_PLACED` | 좌석, 색, `x`·`y`, 수 번호, `timedOut`(자동 한 수였는가) |
| 공개 | `TURN_CHANGED` | 좌석, 색, 흑 차례면 금수 자리 목록 `[{x,y,kind}]`(`DOUBLE_THREE`·`DOUBLE_FOUR`·`OVERLINE`) |
| 공개 | `MATCH_ENDED` | 승자 좌석(무승부 −1), 사유, 승리 줄(5목일 때), 총 수 |
| 비공개 | `ERROR` | `NOT_YOUR_TURN`·`OCCUPIED`·`OUT_OF_BOARD`·`FORBIDDEN_MOVE`(+`kind`)·`MATCH_OVER` |

- 공개 이벤트는 모두 순번을 쓴다(`sequenced()` 기본 true). 비공개는 `ERROR` 뿐이라 `!isPrivate()` 로 둔다(D-126 권장).
- **payload 는 결과값**: `STONE_PLACED` 는 수 번호를 실어 같은 수를 두 번 받아도 같은 판이 된다. `TURN_CHANGED` 는 턴 카운트다운의
  기준(D-131 — 클라 `turnClock` 이 이 이벤트에서 다시 센다)이라 착수마다 반드시 낸다.
- 금수 목록은 **서버가 계산해 싣는다** — 클라에 렌주 판정을 두 번 구현하지 않는다(Server-Authoritative). 공개 뷰에도 같은 목록.
- 액션 type 문자열: 다른 게임과 겹치는 이름(`PLAY_CARD`)을 쓰지 않고 `PLACE_STONE` 으로 — 방이 게임 하나라 충돌은 없지만 로그를 읽기 쉽게.

## 9. 위험과 후속

- **거짓 33 판정 오류**가 가장 큰 룰 위험이다 — 정답이 알려진 렌주 국면으로 테스트를 먼저 만든다(S1 첫 작업). 판정이 틀리면 흑이
  두고 싶은 수를 못 두거나 금수를 둘 수 있어 신뢰가 바로 깨진다.
- **봇 계산이 락 TTL(2초)을 넘는 것** — 노드 상한으로 막고, 어댑터에서 정책 시간을 재 100ms 를 넘으면 WARN 로그(운영에서 측정).
- **관전 훈수** — 친구 판이라 허용. 문제가 되면 사람끼리 판의 관전 채팅을 끄는 방 설정을 후속으로.
- **한 수 템포** — 두 단계 확정이 손에 안 맞으면 S4 실측 뒤 "한 번에 두기" 를 휴대폰에도 열지 결정.
- **v1 제외**: 무르기, 무승부 제안, 렌주 개막 규칙, 룰셋 방 설정(§2.1 D), 흑백 교대, 돋보기, 다시 보기(기보는 저장해 둔다),
  백 봇의 금수 유도 전략.

## 10. 미결 질문

1. **룰셋** — 렌주식 금수 고정(추천) / 삼삼만 금지 / 자유 오목 / 방장이 고르기.
2. **흑백** — 무작위(추천) / 진 사람이 흑(교대) / 방장이 흑.
3. **시간 초과** — 자동 한 수 + 2번 연속 시간패(추천) / 바로 시간패 / 자동 한 수만.
4. **봇 난이도 고르기** — 대기실 방 설정(추천, 포트 확장 1건) / 한 단계만(포트 변경 0).
