## 1. 목표와 성공 기준

요트를 네 번째 게임으로 붙인다. 이 게임은 **손패도 트릭도 비공개 상태도 없다** — 기존 세 게임과 공유하는 모양이 가장
적어서, `multi-game.md` 가 처음부터 "포트가 티츄 모양으로 굳었는지 드러내는 게임"으로 남겨 둔 것이다.

1. **일반 공용 룰** — 주사위 5개, 차례마다 최대 3번 굴림, 12칸 점수표, 상단 보너스.
2. **기다림이 지루하지 않은 순차 진행** — 다른 사람의 굴림·홀드를 실시간으로 지켜본다(§4).
3. **포트 검증** — 포트를 고쳐야 하는 지점을 측정해 기록한다(§5). 예상은 1건(`GameContext.turnSeconds`).

| # | 기준 | 확인 방법 |
| --- | --- | --- |
| 1 | 인프라에 게임 이름 분기 0줄. 인프라 변경은 포트 확장 1건(§5.2) | `grep -rni yacht server/src/main/java/com/mirboard/infra` → 0건 |
| 2 | 1~4인 무작위 봇 시뮬레이션 전부 종료, 매 전이 뒤 불변식(칸 수·점수 합·굴림 횟수) 유지 | 시뮬레이션 테스트(인원별 2,000판) + 불변식 검사기 |
| 3 | 점수 계산이 전 조합(6^5 = 7,776개 × 12칸)에서 명세와 일치 | 전수 테스트(명세 표에서 직접 쓴 기대값 함수와 대조) |
| 4 | 주사위 눈은 서버가 굴린 시점에만 정해진다(상태에 미래 눈·시드 없음) | 상태 직렬화 테스트 |
| 5 | 차례 제한이 "차례 전체"로 걸린다 — 홀드를 계속 바꿔도 제한이 늘지 않음 | 엔진 타이머 단위 테스트 + IT |
| 6 | 티츄·스컬킹·원카드 회귀 0 | `./scripts/check.sh` 전체 |
| 7 | 모바일(375px)에서 4인 점수표가 가로 스크롤 없이 보이고 주사위 터치 영역 44px 이상 | 브라우저 실측 |

## 2. 확정 결정 (사용자, 2026-11-09)

| 항목 | 결정 |
| --- | --- |
| 진행 | **순차**. 한 명씩 굴리고 전원이 그 주사위를 실시간으로 본다 |

| 풀하우스 | **5개 같음도 인정** [하우스 룰] |
| 차례 제한 | 선택지 끔·20·30·45·60, **기본 45초**(차례 전체) |
| 개인 최고 점수 | **v1 제외**(후속) |

기각한 안:

- **동시 진행**(12라운드마다 전원이 자기 점수표를 동시에 굴림) — 기다림은 0 이지만 "남의 세 번째 굴림을 같이 졸이며 보는"
  재미가 사라지고 각자 혼자 하는 게임 + 순위표가 된다. 포트로는 가능하다(`pendingSeats` 여러 좌석 — 티츄 Dealing 선례).
  나중에 방 옵션으로 넣을 수 있게 §10 후속에 남긴다.
- **순차 2~6인** — 6인이면 한 바퀴 1~2분 대기. 상호작용이 없는 게임에서 그만큼 기다리게 할 이유가 없다.

## 3. 룰 (v1 기준선)

### 3.1 진행

| 항목 | v1 |
| --- | --- |
| 인원 | 1~4, 친구 방 정원 4(D-143 — 정원 = 게임 최대, 방장이 "N명으로 시작") |
| 매치 | 12라운드. 라운드마다 좌석 순서대로 한 차례씩. 살아 있는 전원이 12칸을 다 채우면 끝 (1판 = 1매치) |
| 첫 차례 | 좌석 0 **[결정]** — 모두 같은 횟수(12번)를 하므로 선 이점이 없다. 좌석 순서는 방의 좌석 정책을 따른다 |

| 기록 | 1번 이상 굴린 뒤 **빈 칸 하나**에 반드시 기록한다(조건이 안 맞으면 0점 — "버리기"). 기록하면 차례 끝 |
| 3번째 굴림 뒤 | 기록만 할 수 있다 |
| 순위 | 총점 내림차순. 같으면 **동순위 [결정]**(깨는 규칙 없음). 탈주자는 최하위(탈주자끼리 동순위) |

- **제외 [결정]**: 요트 추가 보너스·조커 규칙(요트 칸을 쓴 뒤 또 요트가 나왔을 때의 특례), 13칸 변형(3 카드·찬스 분리 등),
  보너스 기준 변형. 원문마다 갈리는 부분이라 v1 은 가장 단순한 형태로 둔다.
- 칸 이름은 일반 명사(숫자·초이스·포 카드·풀 하우스·스트레이트·요트)만 쓴다. 영어 상표식 칸 이름(예: 1 칸을 부르는 고유 명칭)은 쓰지 않는다.

### 3.3 세부 (S1 에서 확정 — 정본 `docs/rules-yacht.md` §4·§6~§8·§10)

1. **홀드 변경은 굴림 1·2번째 뒤에만** 받는다. 첫 굴림 전·3번째 굴림 뒤·차례가 아닐 때는 `HOLD_NOT_ALLOWED`.
2. **5개 전부 홀드하고 굴리기**는 거절한다(`NOTHING_TO_ROLL`) — 굴림 횟수만 날리는 수라 실수일 뿐이다.
3. **기록 후보 점수**는 서버가 계산해 공개 상태와 `DICE_ROLLED` 에 싣는다(§6.3). 클라는 점수 계산을 하지 않는다.
4. **0점 기록 확인**은 클라 UX 일 뿐 서버는 0점 기록을 그대로 받는다.
5. **차례 제한**은 "차례 전체" 시간이다(§5.2). 시간이 다 되면: 아직 안 굴렸으면 서버가 한 번 굴리고, 그 눈으로 **즉시 점수가 가장 높은 빈 칸**에
   기록한다(같으면 점수표 위쪽 칸). 자동 기록은 `SCORED.auto = true`.
6. **탈주**: 차례에서 빠지고 점수표는 그 자리에서 멈춘다. 탈주자 차례였으면 다음 좌석으로 넘어간다. 사람이 1명 이상 남으면 계속,
   사람이 없으면(봇만 남음) 그 자리에서 현재 총점으로 순위를 매겨 끝낸다(원카드 `NO_HUMANS` 와 같은 판단).
7. **안전장치**: 총 액션 수 상한(기본 좌석 수 × 12 × 40)에 닿으면 남은 칸을 0점으로 보고 현재 총점으로 종료한다. 홀드 토글을 무한히
   보내는 클라를 막는 장치이고, 시뮬레이션에서 발생 0 을 확인한다.

## 4. 기다림 UX — 순차에서 지루하지 않게

4인이면 내 차례는 25%다. 한 차례가 10~20초라 한 바퀴 대기는 30~60초, 한 판은 약 8~12분이다. 기다리는 시간을 "구경"으로 바꾸는 장치:

| 장치 | 내용 | 비용 |
| --- | --- | --- |
| 실시간 굴림 | 차례인 사람의 굴림이 전원 화면 가운데 주사위 판에서 같은 애니메이션으로 굴러간다 | `DICE_ROLLED` 결과값 + 클라 애니메이션 |
| 실시간 홀드 | 무엇을 남기는지 그대로 보인다("요트 노리네") | `DICE_HELD` 1종 (사용자 결정) |
| 후보 점수 미리보기 | 차례인 사람의 점수표 열에 후보 점수가 흐리게 뜬다 — 구경꾼도 "어디 넣을까"를 같이 고민 | 서버가 계산해 싣는다(§3.3-3) |
| 기록 강조 | 기록한 칸이 잠깐 빛나고, 큰 칸(요트·라지 스트레이트·보너스 달성)은 짧은 축하 효과 | 클라만 |
| 내 차례 알림 | 원카드 D-160 처럼 좌석 "차례" 표시 + 내 차례면 진동 1회, 경기장 테두리 빛(D-173) | 클라만, 기존 패턴 재사용 |
| 다음 차례 예고 | "다음: 나" 표시 — 앞사람이 기록하는 순간 바로 굴릴 준비 | 클라만 |
| 채팅 한 줄 | D-163 좌석 위 채팅 한 줄을 그대로 | 공용 훅 재사용 |
| 봇 템포 | 봇 액션 사이 700ms(`mirboard.bot.delay-millis`) — 봇 차례 ≈ 굴림·홀드·굴림·홀드·굴림·기록 6액션 ≈ 4초. 구경하기 알맞은 속도 | 설정 그대로 |

### 5.2 포트 확장 1건 — `GameContext.turnSeconds`

**깨진 가정**: 인프라 턴 타이머는 "액션 하나 = 차례 하나"를 전제한다. 진행 경로는 성공한 액션마다 `onTurnAdvanced` 로 세대를 올리고
턴 데드라인을 `turnSeconds` 로 **처음부터 다시** 건다. 티츄·스컬킹·원카드는 차례당 액션이 1개라 문제가 없었다. 요트는 한 차례가
굴림·홀드·기록 최대 6+액션이고, 홀드 토글을 계속 보내면 차례 제한이 **무한히 늘어난다**.

**안**: 엔진이 차례 시작 시각을 상태에 두고, 포트 ⑦ 엔진 타이머로 "차례 전체" 데드라인을 건다. 그러려면 엔진이 방의 턴 제한을 알아야
하는데 `GameContext` 에는 `(roomId, playerIds, targetScore, stake, botSeats)` 뿐이다. → **`GameContext` 에 `turnSeconds` 를 더한다.**

```java
public record GameContext(String roomId, List<Long> playerIds, int targetScore, int stake,
                          List<Integer> botSeats, int turnSeconds) { ... }   // 0 = 끔. 기존 게임은 무시
```

- 게임 중립이다 — 방 설정이 엔진에 들어오는 유일한 창구라는 `GameContext` 의 정의 그대로이고, `targetScore`·`stake` 처럼 "쓰지 않는
  게임은 무시"한다. 생성 지점은 `GameEngineProvider` 한 곳 + 보조 생성자(테스트·라운드 스타터)라 기존 게임 코드 변경 0.
- `timer(state)` = `turnStartedAt + turnSeconds − now`(턴 제한 끔이면 empty). 재무장해도 처음부터 세지 않는다(포트 ⑦ 계약 그대로).
- `onTimer(state)` = §3.3-5 자동 처리 `Result`. 시스템 전이라 `GameAction` 이 아니다(클라 위조 불가 — 포트 ⑦ 원칙).
- 인프라 턴 타이머(액션마다 다시 걸림)는 그대로 둔다. 마지막 액션 + T ≥ 차례 시작 + T 라 **엔진 타이머가 항상 먼저** 발화하고, 발화가
  세대를 올려 턴 데드라인은 지워진다. 턴 데드라인 쪽 `timeoutAction` 은 폴백으로만 남는다(§6.5).
- resync 의 `turnRemainingMs`(인프라 — 마지막 액션 기준)는 요트에서 부정확하다. 요트 게임판은 공개 뷰의 `turnRemainingMs`(엔진 계산 —
  차례 기준)를 쓴다. 인프라 쪽을 고치지 않는 이유: 다른 세 게임은 둘이 같다.

**대안(포트 무변경, 기각 추천)**: 차례당 홀드 변경 횟수 상한(예: 굴림당 20회) + 액션마다 리셋되는 제한을 "결정 하나당 제한"으로 받아들인다.
포트는 안 바뀌지만 "30초 제한"이 실제로는 최대 3~4배가 되고 사용자에게 설명하기 어렵다.

**오목과의 관계**: 오목 기획(D-176)도 `GameContext` 에 `options` 를 더한다. 같은 레코드를 바꾸므로 **먼저 착수하는 쪽이 두 필드를 한 변경으로** 넣는다.
`turnSeconds` 는 모든 게임에 통하는 설정이라 `RoomOption`(게임이 선언하는 옵션) 맵에 넣지 않고 따로 필드로 둔다.

**의의**: `multi-game.md` 가 예상한 "깨지는 지점"(비공개 뷰·12칸 종료·조합 폭발)은 전부 이미 포트에 들어 있었다. 실제로 드러난 것은 그 표에
없던 **"한 차례 = 한 액션" 가정**이다 — 케이스 스터디(`docs/case-study-multi-game.md`)에 넣을 측정 결과.

## 6. 서버 설계

### 6.1 패키지 `domain.game.yacht`

원카드·스컬킹의 2계층(순수 룰 엔진 + 포트 어댑터)을 따른다. 괄호는 만드는 단계.

```
yacht/
  YachtGameDefinition    @Component · ID "YACHT" · 1~4인 · 상태 COMING_SOON(→ 공개는 별건, D-168 의 MIRBOARD_*_STATUS 패턴) (S3)
  YachtEngine            순수 룰 엔진 — 저장소·시계 없음, 주사위·시각은 인자로 (S2)
  YachtGameEngine        포트 어댑터 — 상태 저장·시계·Random·로컬 발행·엔진 타이머 (S3)
  dice/       Dice(5개 눈 불변 레코드) · HoldMask(5비트) · DiceRoller(주입용 함수형 인터페이스) (S2)
  score/      Category(12칸 enum, 점수표 순서) · Scoring(눈 → 칸별 점수, 순수 함수) · Scorecard(칸별 점수|빈 칸, 소계·보너스·총점) (S2)
  state/      YachtState · TurnState · MatchResult · YachtStateMapper(공개 뷰) (S2)
  action/     YachtAction(sealed: Hold · Roll · Score) · RejectionReason · YachtActionRejectedException (S2)
  rules/      Ranking(총점·탈주 → 순위) (S2)
  event/      YachtEvent(sealed) (S2) · YachtMatchCompleted (S3)
  invariant/  YachtInvariantChecker (S2)
  bot/        YachtBotPolicy · YachtBotView (S3)
  lifecycle/  YachtRoundStarter(GameStartingEvent → 첫 상태) (S3)
  persistence/ YachtStateStore · YachtMatchRecorder · YachtHeadToHead (S3)
```

S2 에서 처음 그림과 달라진 점: 엔진은 `GameContext`(좌석 수·봇 좌석)와 `turnSeconds` 를 생성자로 받는다(`GameContext.turnSeconds` 는 S3 의
포트 확장이라 S2 에서는 따로 넘긴다). 엔진이 만드는 비공개 이벤트는 **0종**이다 — 거절은 예외 코드로 인프라가 `ERROR` 를 보내므로
`YachtEvent` 는 전부 공개이고 `sequenced()` 를 재정의하지 않는다. 액션 상한에 닿은 전이는 다음 차례 알림을 지우지 않고 그 뒤에 `MATCH_ENDED` 를 붙인다
(공개 뷰의 라운드와 이벤트가 어긋나지 않게).

### 6.2 상태

불변 레코드. 원카드처럼 엔진 안에서만 가변 사본을 고쳐 새 레코드로 얼린다.

- `YachtState`: 좌석별 `Scorecard` · 라운드(1~12) · 차례 좌석(끝나면 −1) · `TurnState` · 탈주 좌석 집합 · 총 액션 수 · 버전 · 결과(끝나기 전 null).
- `TurnState`: 주사위(첫 굴림 전 null) · 홀드 마스크 · 굴린 횟수(0~3) · 차례 시작 시각(epoch ms — 어댑터가 넣음).
- **미래 눈·시드를 상태에 두지 않는다 [결정]** — 눈은 `Roll` 을 적용하는 순간 어댑터의 `Random` 으로 정한다. 상태 어디에도 "다음 눈"이 없으니
  상태가 새도 예측할 것이 없다. 재현이 필요한 테스트는 순수 엔진에 `DiceRoller` 를 주입한다.
- 불변식: 좌석별 채운 칸 수 ∈ {라운드−1, 라운드}(차례 순서에 맞게) · 탈주자 제외 · 굴린 횟수 ≤ 3 · 주사위가 null 이면 굴린 횟수 0 · 총점 = 칸 합 + 보너스 ·
  끝났으면 살아 있는 전원 12칸.

### 6.3 액션과 이벤트 (STOMP)

| 방향 | type | 내용 |
| --- | --- | --- |
| 클라→서버 | `HOLD` | `held`(5개 불리언 배열). 굴림 1·2번째 뒤에만 |
| 클라→서버 | `ROLL` | 홀드 안 한 주사위를 굴린다. (선택) `held` 를 실어 보내면 먼저 적용 — 홀드 이벤트가 늦게 도착해도 굴림이 의도대로 |
| 클라→서버 | `SCORE` | `category` |
| 공개 | `TURN_CHANGED` | 좌석, 라운드, 차례 제한(초, 0 = 끔) |
| 공개 | `DICE_HELD` | 좌석, `held` |
| 공개 | `DICE_ROLLED` | 좌석, 주사위 5개, `held`, 굴린 횟수, **후보 점수**(빈 칸별 점수 — 서버 계산) |
| 공개 | `SCORED` | 좌석, 칸, 점수, 그 좌석의 상단 소계·보너스·총점, `auto`(시간 초과 자동 기록) |
| 공개 | `PLAYER_ELIMINATED` | 좌석, 사유 `DESERTED`, 멈춘 총점 |
| 공개 | `MATCH_ENDED` | 순위(좌석·총점·순위), 사유 `FINISHED` / `NO_HUMANS` / `ACTION_LIMIT` |
| 비공개 | `ERROR` | `NOT_YOUR_TURN`, `HOLD_NOT_ALLOWED`, `HOLD_UNCHANGED`, `NOTHING_TO_ROLL`, `NO_ROLLS_LEFT`, `NOT_ROLLED_YET`, `CATEGORY_FILLED`, `MATCH_OVER`, `INVALID_ACTION` — 인프라가 예외 코드로 보낸다(엔진 이벤트 아님) |

- 이벤트 type 문자열은 게임 간 재사용(`TURN_CHANGED`·`PLAYER_ELIMINATED`·`MATCH_ENDED`) — 방 단위 토픽이라 충돌 없음.
- **엔진의 비공개 이벤트는 없다**(S2) — `ERROR` 는 인프라가 거절 예외로 만든다. 그래서 `YachtEvent` 는 전부 공개·순번 있음(기본값)이다.
- **공개 payload 는 결과값**(원카드 원칙): `DICE_ROLLED` 는 주사위 전체·홀드·횟수, `SCORED` 는 소계·총점까지. 두 번 적용해도 같고 하나 빠져도 다음 이벤트가 맞춘다.
- `MATCH_STARTED` 는 두지 않는다 — 시작 상태는 resync 로(원카드 D-129 와 같은 결론). 첫 `TURN_CHANGED` 만 시작 직후 발행.
- 공개 뷰도 같은 원칙: 좌석별 점수표(칸별 점수|null)·소계·보너스·총점·탈주 여부, 차례 좌석, 라운드, 주사위·홀드·굴린 횟수, 후보 점수, `turnRemainingMs`(엔진 계산), 결과.

### 6.4 흐름

```
TURN_CHANGED(seat=A, round=r)          ← 차례 시작 시각 기록, 홀드 해제, 엔진 타이머 = 차례 제한
 ├ A: ROLL  → DICE_ROLLED(n=1, 후보)
 ├ A: HOLD  → DICE_HELD   (0회 이상, 굴림 사이에만)
 ├ A: ROLL  → DICE_ROLLED(n=2, 후보)
 ├ A: HOLD  → DICE_HELD
 ├ A: ROLL  → DICE_ROLLED(n=3, 후보)
 └ A: SCORE → SCORED      ─┬ 다음 좌석 있음 → TURN_CHANGED(다음, r 또는 r+1)
                           └ 12칸 다 참   → MATCH_ENDED
 (차례 제한 도달 → onTimer: 필요하면 굴림 1회 + 최고점 칸 자동 기록 → 위와 같은 다음 단계)
```

### 6.5 봇·시간 초과

- **봇 정책 `YachtBotPolicy`**(`botAction` override, D-118·D-119 원칙 — 공개 정보만, 결정적, `random` 미사용):
  - 굴림 0회 → `ROLL`.
  - 굴림 1·2회 → 홀드 마스크 32개마다 "남은 굴림으로 얻을 기대 최고 칸 가치"를 전수 계산(최대 6^5 경우 — 액션당 수 ms)해 가장 좋은 마스크를 고른다.
    지금 홀드와 다르면 `HOLD`(구경꾼에게 보이게), 같으면 `ROLL`. 지금 눈의 가치가 기대값 이상이면 바로 `SCORE`.
  - 칸 가치 = 점수 + 상단 보너스 진행 가중(목표 63 에 대한 "눈 × 3" 기준 대비) − 그 칸을 지금 쓰는 기회비용(요트·라지 스트레이트처럼 나중에 노릴 칸을 일찍 0 으로 버리지 않게).
  - 버려야 할 때는 기대 손실이 가장 작은 칸(보통 1 칸·요트 순)에 0 을 쓴다.
- **어댑터 폴백**: 정책이 예외·null·비합법 수를 내면 ERROR 로그 후 `timeoutAction`(포트 권장 패턴).
- **`timeoutAction`**(턴 데드라인 폴백·탈주 아닌 자동 처리): 굴림 0회면 `ROLL`, 아니면 즉시 점수가 가장 높은 빈 칸에 `SCORE`(같으면 위 칸). 봇 정책과 섞지 않는다.
- **강도 확인**(S3, 시드 고정 1,000판): 휴리스틱 봇 평균 총점이 무작위 봇(포트 기본 — 합법수 균등)과 "탐욕 봇(굴리지 않고 바로 최고점 기록)"보다 높고,
  탐욕 봇 1:1 승률이 0.5 를 넘을 것. 절대 수치(평균 몇 점)는 실측 뒤 회귀 기준으로 고정한다.

### 6.6 탈주·종료·기록

- **탈주**(`desert`): §3.3-6. 사람이 남으면 `MATCH_CONTINUES`, 없으면 `MATCH_ENDED(NO_HUMANS)`. 이미 탈주한 좌석이면 `NOT_APPLICABLE`(D-122).
- **정상 종료**: 사람만의 방·봇이 낀 방 모두 D-153·D-174 대로 대기실 복귀(인프라가 처리 — 요트는 손댈 것 없음).
- **기록 V(다음 번호)**: `yacht_match_results`(room_id, finished_at, end_reason, payload_json) + `yacht_match_participants`(match_id, user_id, seat, final_rank,
  total_score, is_win, deserted). 스컬킹·원카드의 2테이블 구조 그대로. 마이그레이션 번호는 착수 시점에 정한다(다른 기획 세션도 V13 을 노린다).
- **`YachtMatchRecorder`**: 로컬 발행 `YachtMatchCompleted` 구독(D-116). 매치 기록기 계약 3가지(`RatedMatchPolicy.eloApplies` · 비봇 참가자마다
  `user_game_stats` · 발행 지점에서 실패 격리)를 따른다. 승리 = 1등(동순위면 모두). ELO 는 `EloCalculator.applyFreeForAll`, 점수 = 좌석 수 − 순위.
- **1인 매치 (D-181)**: 결과·참가자·`user_game_stats` **아무것도 쓰지 않는다**. 셋 중 일부만 쓰면 게스트 정리 계약(기록기 계약 2)이 깨지고,
  상대 없는 판의 승패는 뜻이 없다. 개인 최고 점수는 §10 후속.
- **상대 전적**: `YachtHeadToHead`(`HeadToHeadSource`) — 최종 순위로 센다(원카드와 같다).
- **카탈로그**: `minPlayers=1`·`maxPlayers=4`·`defaultPlayers=4`·`supportedRoomOptions` 빈 집합(목표 점수·팀·판돈 없음)·
  `turnSecondsChoices` = 끔·20·30·45·60, `defaultTurnSeconds` = 45(§2) — 차례 전체 시간이라 원카드(한 수)보다 길게.

### 6.7 상태 은닉

비공개 상태가 없다. 그래도 지킬 것:

- 상태에 미래 눈·시드·RNG 상태를 두지 않는다(§6.2) — 공개 뷰 직렬화 테스트가 아니라 **상태 직렬화 테스트**로 고정.
- 봇 정책의 내부 평가값(기대값 표)은 로그·이벤트에 싣지 않는다(무엇을 노리는지는 홀드로만 드러난다).

- 굴림 애니메이션 ~600ms, `prefers-reduced-motion` 이면 즉시 표시. 봇 템포(700ms) 안에 끝나야 한다.
- 관전자: 버튼 없음, 모든 정보는 같다(비공개가 없다).
- 종료: 게임판 유지 + 순위 카드(`YachtMatchEnd`), D-153 대기실 복귀면 [대기실로].

## 10. 위험과 후속

- **템포**: 봇 700ms × 6액션이 빠르거나 느릴 수 있다 — 설정값은 전역이라 게임별로 못 바꾼다. 실측 뒤 문제면 클라 애니메이션 큐(서버 무변경)로 먼저 흡수한다.
- **인프라 `turnRemainingMs` 불일치**(§5.2) — 요트 화면은 엔진 값을 쓰므로 사용자 영향은 없다. 공용 카운트다운 컴포넌트를 쓰게 되면 그때 정리.
- **4인 기다림**이 실측에서도 길면 → 동시 진행을 방 옵션(`RoomOption`)으로 추가하는 후속(포트는 이미 여러 대기 좌석을 지원).
- **후속 후보(v1 제외)**: 동시 진행 옵션 · 개인 최고 점수(1인 판 기록 — 별도 테이블, 계정 컬럼 아님) · 요트 추가 보너스 변형 · 내기 칩(D-82 일반화 별건).
- **무료 범위**: 새 상시 프로세스·외부 서비스 없음. Redis 키 1종(상태)·DB 테이블 2개만 늘어난다.
