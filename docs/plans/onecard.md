## 1. 목표와 성공 기준

원카드를 세 번째 게임으로 붙인다. 핵심은 두 가지다.

1. **표준 기본형 룰** — 공격 카드 누적·특수 카드·파산이 있는 한국식 원카드.
2. **"원카드!/잡기!" 실시간 경쟁** — 손패가 1장이 되면 전원에게 같은 무작위 위치에 버튼이
   뜬다. 지금 포트에는 "시간이 지나면 저절로 바뀌는 상태"가 없어 포트를 한 번 넓힌다(§4.5).

성공 기준:

| # | 기준 | 확인 방법 |
| --- | --- | --- |
| 1 | 인프라에 게임 이름 분기 0줄. 인프라 변경은 포트 확장 2건(엔진 타이머 §4.5, 비순번 이벤트 §4.5b) | `grep -rni onecard server/src/main/java/com/mirboard/infra` → 0건 |
| 2 | 2~6인 무작위 봇 시뮬레이션이 전부 종료, 매 전이 뒤 카드 54장 보존 | 시뮬레이션 테스트(인원별 2,000판) + 불변식 검사기 |
| 3 | 경쟁 5개 시나리오 통과: 사람 먼저·봇 먼저·무응답·동시 누름·창 중 탈주 | 통합 테스트 |
| 4 | 공개 뷰·토픽 이벤트에 손패 카드와 봇 반응 시각이 없음 | 직렬화 테스트 |
| 5 | 티츄·스컬킹 회귀 0 | `./scripts/check.sh` 전체 |
| 6 | 모바일에서 경쟁 버튼 터치 영역 44px 이상, 손패·좌석을 가리지 않음 | 브라우저 실측 |

## 2. 확정 결정 (사용자, 2026-10-04)

| 항목 | 결정 |
| --- | --- |
| 룰셋 | 표준 기본형(§3) |
| 외치기 | 전원 버튼 실시간 경쟁. 서버가 고른 무작위 위치(사전 정의한 안전 슬롯 + 지터)에, 전원에게 같은 위치로 뜬다 |
| 봇 | 사람처럼 반응 시간(기본 1.0~2.5초)을 갖고 경쟁에 참여 |
| 진행 | 경쟁이 끝날 때까지(첫 누름 또는 3초) 다음 차례를 멈춘다 |
| 타이머 구현 | 포트에 선택형 **엔진 타이머** 추가(A안) |

기각한 안:

- **B. 기존 봇 루프·턴 타이머 재활용** — 턴 제한을 끈 방(`turnSeconds=0`)에서는 창이 닫히지
  않는다. 봇 지연이 고정값(`mirboard.bot.delay-millis`, 기본 700ms)이라 반응 시간을 무작위로
  줄 수 없다. 결국 포트를 고쳐야 한다.
- **C. 클라가 3초를 재고 결과를 보고** — Server-Authoritative 위반.

## 3. 룰 (v1 기준선)

### 3.1 확정

| 항목 | v1 |
| --- | --- |
| 인원 | 2~6, 기본 4. 54장(52 + 조커 2)에서 6인 × 7장 = 42장을 나눠도 뽑을 더미가 남는 상한 |
| 분배 | 7장씩. 남은 카드는 뽑을 더미, 그중 1장을 뒤집어 시작 |
| 내기 | 맨 위 카드와 무늬 또는 숫자가 같아야 한다. 7 로 지정된 무늬가 있으면 그 무늬 |
| 공격 | 2(+2) · A(+3) · 흑백 조커(+5) · 컬러 조커(+7). 누적되고, 받는 사람은 반격하거나 누적 장수를 먹는다 |
| 반격 | 같은 숫자의 공격 카드, 또는 더 센 공격 카드. 조커 공격은 조커로만 |
| 특수 | J 다음 사람 건너뜀 · Q 방향 반전 · K 한 번 더 · 7 무늬 변경(낼 때 지정) |
| 먹기 | 낼 수 없거나 내지 않으면 먹는다. 공격 중이면 누적 장수, 아니면 1장 |
| 파산 | 손패가 20장 이상이 되면 탈락. 그 손패는 뽑을 더미 아래로 |
| 외치기 | 카드를 낸 결과 손패가 정확히 1장이면 경쟁 창이 열린다. 주인은 "원카드!", 나머지는 "잡기!". 먼저 누른 쪽이 이긴다. 잡히면 주인이 1장 먹는다. 3초 동안 아무도 안 누르면 벌칙 없이 진행 |
| 종료 | 누군가 손패를 다 내면 즉시 매치 종료(1판 = 1매치). 탈락으로 1명만 남거나 살아 있는 사람이 없으면(봇만 남음) 그 자리에서 종료 |
| 순위 | 1등은 다 낸 사람. 나머지는 남은 장수가 적은 순(같으면 동순위). 파산자는 그 아래(늦게 파산한 쪽이 위), 탈주자는 최하위 |
| 덱 소진 | 뽑을 더미가 비면 버린 더미의 맨 위만 남기고 섞어 다시 쓴다 |
| 제외 | ♠A 특례, 3 방어, 폭탄, 계단(연속 내기), 같은 숫자 동시 내기 |

### 3.2 세부 (S1 에서 확정 — 정본 `docs/rules-onecard.md`, D-125)

> 아래는 S1 에 넣은 기본안이다. 정본에서 바뀐 것: 7(2인 → **살아 있는 2명**, §8.1), 8(일반 카드가 없으면
> 처음부터 다시 나누기 추가, §3-5), 10(낼 카드가 있어도 0장을 먹으면 패스, §11.3).

1. **공격 세기 순서**: 2 < A < 흑백 조커 < 컬러 조커. 반격은 맨 위 공격 이상이어야 한다.
   같은 숫자는 무늬와 무관하다. 더 센 숫자 카드(2 위의 A)는 일반 내기처럼 무늬가 맞아야
   한다. 조커는 무늬와 무관하다. 그래서 흑백 조커는 컬러 조커로만 막고, 컬러 조커는 못 막는다.
2. **공격 중에는** 7·J·Q·K 를 낼 수 없다(반격 수단이 아니다).
3. **먹은 뒤**에는 차례가 끝난다. 먹은 카드가 낼 수 있는 카드여도 바로 내지 못한다.
4. **낼 수 있어도 먹기**를 허용한다(전략적 먹기).
5. **조커 다음 카드**: 공격을 받아 먹은 뒤에는 무늬 제한이 없다(아무 카드나).
6. **7 내기 조건**: 일반 카드처럼 무늬나 숫자가 맞아야 낼 수 있다.
7. **2인 게임**: J 와 Q 모두 "한 번 더"로 동작한다.
8. **시작 카드**가 공격·특수 카드면 숫자 카드가 나올 때까지 다시 뒤집는다(첫 차례에 공격을
   떠안는 불공정 제거).
9. **K 로 손패가 1장**이 되면 경쟁 창이 먼저 열리고, 해소 뒤 같은 사람이 이어서 낸다.
   마지막 카드가 K·공격 카드여도 종료를 인정한다.
10. **교착**: 뽑을 더미와 다시 쓸 버린 더미가 모두 비어 먹을 수도 낼 수도 없으면 그 차례는
    패스. 살아 있는 전원이 연달아 패스하면 남은 장수 순으로 종료한다.
11. **안전장치**: 총 차례가 상한(기본 600)에 닿으면 교착과 같이 남은 장수 순으로 종료한다.
    시뮬레이션에서 발생 빈도가 0 에 가까운지 확인한다.
12. **누적 장수가 남은 카드보다 많으면** 가능한 만큼만 먹는다.

## 4. 설계

### 4.1 서버 패키지 `domain.game.onecard`

스컬킹의 2계층(순수 룰 엔진 + 포트 어댑터)을 그대로 따른다. 괄호는 만드는 단계다.

```
onecard/
  OneCardGameDefinition   @Component · ID "ONE_CARD" · 2~6인 · COMING_SOON → S4 에서 AVAILABLE (S3)
  OneCardEngine           순수 룰 엔진 — 저장소·시계 없음, 난수는 주입 (S2)
  OneCardGameEngine       포트 어댑터 — 상태 저장(Redis)·시계·로컬 발행 (S3)
  Dealer · RaceSettings   분배·시작 카드 / 창 길이·봇 반응 구간·슬롯 수 (S2)
  card/        Suit · Joker · PlayingCard(역할·공격 값과 세기) · Deck (S2)
  state/       OneCardState · RaceWindow · Elimination · MatchResult (S2)
  action/      OneCardAction(sealed: PlayCard·Draw·CallOneCard·Catch) · RejectionReason ·
               OneCardActionRejectedException (S2)
  rules/       PlayRules(낼 수 있나·반격) · TurnOrder(J·Q·K·탈락 건너뛰기) · Ranking(순위) (S2)
  event/       OneCardEvent(sealed) (S2) · OneCardMatchCompleted (S3)
  invariant/   OneCardInvariantChecker(54장 보존 등) (S2)
  bot/         OneCardBotPolicy(공개 정보 뷰만 본다) (S3)
  lifecycle/   OneCardRoundStarter(GameStartingEvent → 분배) (S3)
  persistence/ OneCardStateStore, OneCardMatchRecorder (S3)
```

S2(D-127)에서 처음 그림과 달라진 점: 단계 enum(`Phase`)·`ActionValidator`·`AttackRules`·`race/` 패키지는
만들지 않았다. 단계는 상태에서 파생하고(§4.2), 검증과 경쟁 창 처리는 엔진 안에, 공격 값·세기는 카드에 뒀다 —
각각 엔진 안 몇 곳에서만 쓰여 따로 뺄 이유가 없었다.

### 4.2 상태

불변 레코드다. 한 전이가 여러 필드를 함께 바꾸므로 `with*` 대신 엔진 안에서만 가변 사본을 고쳐 새 레코드로
얼린다(D-127).

- `OneCardState`: 좌석별 손패 · 뽑을 더미(0번이 맨 위) · 버린 더미(마지막이 맨 위) · 차례 좌석(창이
  열렸거나 끝났으면 −1) · 방향(±1) · 지정 무늬(7) · 공격 누적 장수 · 경쟁 창(없으면 null) · 탈락 목록(탈락 순) ·
  연속 패스 수 · 총 차례 수 · 버전(전이마다 오른다 — 탈락이 낀 전이는 +2, 비공개 손패 이벤트의 `handVersion`) · 결과(끝나기 전엔 null).
  공격 세기는 맨 위 카드에서, K 보너스 차례는 차례 좌석에서, 단계(`PLAYING`/`RACE`/`ENDED`)는 창·결과
  유무에서 파생한다.
- `RaceWindow`: `raceId`(창을 연 전이의 버전) · 주인 좌석 · 슬롯 · 지터 · 연 시각 · 창 길이 · 낸 순간 정해 둔
  다음 차례(§9.2) · **가장 빠른 봇의 좌석·행동·지연**(서버 전용)

첫 누름이 창을 닫으므로 봇은 가장 빠른 한 명만 기억하면 된다.

### 4.3 액션과 이벤트 (STOMP)

| 방향 | type | 내용 |
| --- | --- | --- |
| 클라→서버 | `PLAY_CARD` | `card`, 7 이면 `declaredSuit` |
| 클라→서버 | `DRAW` | 공격 중이면 누적 장수, 아니면 1장 |
| 클라→서버 | `CALL_ONE_CARD` | `raceId`. 창 주인만 |
| 클라→서버 | `CATCH` | `raceId`. 창 주인 외 |
| 공개 | `MATCH_STARTED` | 첫 차례 좌석, 시작 카드, 손패 장수, 뽑을 더미 장수 |
| 공개 | `CARD_PLAYED` | 좌석, 카드, 지정 무늬, 낸 뒤 손패 장수, 공격 누적, 낸 뒤 방향(Q 로 창이 열리면 `TURN_CHANGED` 가 늦다) |
| 공개 | `CARDS_DRAWN` | 좌석, **장수만**, 사유(`TURN`/`ATTACK`/`PENALTY`), 먹은 뒤 손패 장수, 뽑을 더미 장수 |
| 공개 | `TURN_CHANGED` | 좌석, 방향, 공격 누적 |
| 공개 | `RACE_OPENED` | `raceId`, 주인 좌석, 슬롯, 지터, 창 길이 |
| 공개 | `RACE_RESOLVED` | `raceId`, 결과(`CALLED`/`CAUGHT`/`EXPIRED`, 창 중 탈주면 `CANCELLED`), 누른 좌석 |
| 공개 | `PILE_RESHUFFLED` | 뽑을 더미 장수 |
| 공개 | `PLAYER_ELIMINATED` | 좌석, 사유(`BANKRUPT`/`DESERTED`), 탈락 때 들고 있던 장수, 손패를 넣은 뒤 뽑을 더미 장수 |
| 공개 | `MATCH_ENDED` | 순위, 사유(`FINISHED`/`LAST_STANDING`/`STALEMATE`/`NO_HUMANS`) |
| 비공개 | `HAND_DEALT` | 내 손패 전체 + `handVersion` |
| 비공개 | `HAND_UPDATED` | 내 손패 전체 + 새로 받은 카드 + `handVersion`(내기·먹기·벌칙·탈락마다, D-127) |
| 비공개 | `ERROR` | `NOT_YOUR_TURN`, `RACE_IN_PROGRESS`, `NO_RACE` 등 |

이벤트 type 문자열은 게임 간에 재사용된다(`TURN_CHANGED` 등). 방 단위 토픽이라 충돌이 없다.

계획 단계에서 확인한 사실로 정한 payload 원칙 (2026-10-04):

- **비공개 이벤트는 공개 순번을 쓰지 않는다**(§4.5b). 지금은 비공개 이벤트도 방 공통 순번을
  소비해, 그 이벤트를 못 받는 다른 클라에게는 다음 공개 이벤트가 구멍(gap)으로 보이고 resync 를
  부른다. 원카드는 내거나 먹을 때마다 비공개 `HAND_UPDATED` 가 나가므로 이대로면 매 차례 전원이
  resync 한다.
- **비공개 payload 는 손패 전체 + `handVersion`**(상태 버전이라 좌석마다 단조 증가). 클라는 가진 것보다 낮은
  버전을 버린다 — 순번이 없어도 resync 스냅샷(비공개 뷰에도 `handVersion`)과 순서가 뒤바뀌어
  손패가 되돌아가지 않는다.
- **공개 payload 는 증감이 아니라 결과값**(좌석 손패 장수, 맨 위 카드, 지정 무늬, 공격 누적, 방향,
  뽑을 더미 장수). resync 는 잠금 없이 상태와 순번을 따로 읽어, 그 사이 액션이 끼면 이벤트가 두 번
  적용되거나 하나가 빠질 수 있다. 결과값이면 두 번 적용해도 같고, 빠져도 다음 이벤트에서 맞춰진다.

### 4.4 경쟁 창 흐름

```
A 가 카드를 내 손패 1장
 └▶ 엔진: 카드 효과 적용 → 창 열기
      서버 추첨: 슬롯·지터, 봇마다 반응 지연 → 가장 빠른 봇 1명만 기록
      공개: CARD_PLAYED, RACE_OPENED
      pendingSeats = []   (봇 루프·턴 타이머가 끼어들지 않는다)
      인프라: 엔진 타이머 = min(가장 빠른 봇 지연, 3초)
        ├─ 사람이 먼저 누름(STOMP) ─ 방 락을 먼저 잡은 요청이 이김 → RACE_RESOLVED
        ├─ 봇 지연 도달(엔진 타이머) ─ 그 봇의 CALL/CATCH → RACE_RESOLVED
        └─ 3초 도달(엔진 타이머) ─ EXPIRED, 벌칙 없음
 └▶ 해소 뒤: 카드 효과대로 다음 차례(K 면 A 다시) → 봇 루프·턴 타이머 재무장
```

판정 규칙:

- 주인의 `CALL_ONE_CARD` 가 먼저면 `CALLED`(안전). 다른 사람의 `CATCH` 가 먼저면 `CAUGHT` —
  주인이 1장 먹는다(비공개 `HAND_UPDATED` + 공개 `CARDS_DRAWN(PENALTY)`).
- "먼저"는 **방 액션 락을 먼저 잡은 요청**이다. 락 경합으로 `BUSY` 를 받으면 클라는 창이 아직
  열려 있는 동안 짧게 재시도한다(최대 2회 — 락을 쥔 쪽이 창과 무관한 거절 처리일 수 있다).
  이미 해소돼 `NO_RACE` 를 받으면 오류 대신 "늦었어요"를 짧게 보여 준다.
- `raceId` 가 현재 창과 다르면 `NO_RACE` — 늦게 도착한 누름이 다음 창에 붙지 않게 한다.
- 창이 열린 동안 `PLAY_CARD`·`DRAW` 는 `RACE_IN_PROGRESS` 로 거절한다.
- 봇 반응: 창마다 봇 좌석별로 구간 안에서 균등 추첨한다. 기본은 주인·잡는 쪽 모두
  1000~2500ms이고 두 구간을 따로 설정할 수 있다(`mirboard.onecard.bot-reaction-*`). 가장 빠른
  봇이 3초 안이면 그 봇이 누른다.
- 슬롯: 클라가 게임판 기준 상대 좌표로 정의한 N개(프로토콜 상수, 기본 8) 중 서버가 하나를
  고르고, 지터(x·y 각각 −100~100 정수, 클라가 슬롯 반경의 백분율로 환산)를 더한다. 전원이 같은
  위치를 받으므로 위치 운은 공평하다.

**공정성.** 판정이 서버 도착 순서라 핑이 낮을수록 유리하다(`multi-game.md` §7 이 할리갈리
판정 모델로 남겨 둔 선택지 중 "서버 도착 순서"). 버튼을 찾는 시간(수백 ms)이 핑 차(수십 ms)보다
커서 영향이 묻힌다고 본다. 배포 후 경쟁 결과 로그(사람·봇 승률, 반응 시간 분포)로 확인한다.

### 4.5 포트 확장 — 엔진 타이머

**구현됨(S3, D-128)** — 정본은 `docs/game-port.md` §2 "시간이 지나면 일어나는 전이". 발화는 새
`EngineTimerScheduler`(`deadlines:game`)가 맡고 무장은 아래대로 `TurnTimeoutScheduler.onTurnAdvanced` 다.

```java
/** 이 상태에 시간이 지나면 저절로 일어나는 전이가 있으면, 지금부터 남은 시간. 기본: 없음. */
default Optional<Duration> timer(GameState state) { return Optional.empty(); }

/** timer 만료 시의 전이. 발화를 신뢰한다(세대 번호가 "그 사이 상태 무변경"을 보장). */
default Optional<Result> onTimer(GameState state) { return Optional.empty(); }
```

- **무장**: `TurnTimeoutScheduler.onTurnAdvanced` 가 턴 데드라인과 함께 엔진 타이머도 건다(새
  데드라인 종류 `game`, 같은 세대 번호). 사람 액션·봇·턴 타임아웃·탈주·라운드 시작 5곳이 이미
  이 메서드를 부르므로 **호출 지점 변경은 0**이다. 턴 제한을 끈 방에서도 엔진 타이머는 걸린다.
- **발화**: 턴 타임아웃과 같은 가드(세대 → IN_GAME → 락 `tryAcquire`, 실패 시 200ms 재시도 →
  락 안 재확인)를 공유하고, 적용 단계만 `timeoutAction` 대신 `onTimer` 다. 결과는 기존 경로를
  탄다: 저장 → `matchProgress.advance` → 브로드캐스트 → 봇·타이머 재무장.
  **구현 정정(S3 최종 리뷰, D-128)**: 위 코드 주석의 "발화를 신뢰한다 / 세대 번호가 상태 무변경을 보장"은 틀렸다 —
  진행 경로 대부분이 락을 푼 뒤에 세대를 올려 락 해제와 세대 상승 사이에 틈이 있고, 그 틈에 만기된 옛 타이머는
  세대 검사를 통과할 수 있다. 구현은 락 안에서 `timer(state)` 를 다시 물어 **0 이하일 때만** `onTimer` 를 부른다
  (비어 있으면 끝, 남았으면 같은 세대로 그 시간 뒤에 다시 걸고 끝, 만기인데 `onTimer` 가 비면 WARN). 정본은
  `docs/game-port.md` §2.
- **남은 시간**: 재무장해도 처음부터 다시 세지 않도록 "지금부터 남은 시간"을 돌려준다. 원카드는
  창을 연 시각을 상태에 기록하고, 어댑터가 가진 시계로 계산한다(순수 엔진은 시각을 인자로 받음).
- **취소**: `cancel()` 은 두 종류를 함께 지운다. 티츄·스컬킹은 기본 구현(타이머 없음)이라 동작이
  바뀌지 않는다. 대가는 액션마다 상태 조회 1회(Redis GET) 추가.
- **왜 `GameAction` 이 아니라 `Result` 인가**: 클라 JSON 으로 역직렬화되는 액션 계층에 "창
  닫기" 같은 시스템 액션을 넣으면 클라가 위조해 보낼 수 있다. 시스템 전이는 액션 계층 밖에 둔다.
- **왜 창 동안 `pendingSeats` 를 비우는가**: 고정 지연의 봇 루프가 끼어들지 않고, 턴 타이머가
  엉뚱한 좌석을 겨누지 않게 하려는 것이다. 창 동안의 시간 진행은 엔진 타이머 하나가 맡는다.
- **불변식**: 창이 열린 동안의 성공 전이(누름·엔진 타이머·탈주)는 전부 창을 닫는다.
- 할리갈리처럼 실시간 판정이 필요한 후속 게임도 이 확장을 그대로 쓸 수 있다.

### 4.5b 포트 확장 — 비순번 이벤트

**S3 에서 만들지 않았다(D-128, 사용자 결정)** — 같은 확장을 D-126(티츄 resync)이 넣는다. D-126 이 병합되면 원카드
비공개 이벤트 2종에 `sequenced()` 를 false 로 재정의만 더한다(S4 착수 조건). 그 전까지 원카드 비공개 이벤트도
방 순번을 쓴다. 아래는 원래 설계다.

```java
/** false 면 envelope 에 seq 를 붙이지 않는다(순번을 소비하지 않음). 기본 true — 기존 게임 동작 그대로. */
default boolean sequenced() { return true; }
```

- `GameEventBroadcaster` 는 `sequenced()` 가 false 인 이벤트에 `RoomSeq.next` 를 부르지 않고
  seq 를 비운다(`NON_NULL` 이라 JSON 에서 빠진다). 게임 이름을 보지 않는 판단이다.
- 원카드는 비공개 이벤트(`HAND_DEALT`·`HAND_UPDATED`)만 false 로 둔다.
- **기본값이 true 인 이유**: 티츄는 이 resync 에 기대고 있다(§7). 기본을 바꾸면 티츄 동작이 바뀐다.

### 4.6 봇

- **일반 차례**(`botAction` override): 공개 정보 뷰(내 손패 + 공개 상태)만 본다(D-118·D-119 원칙).
  - 공격을 받는 중이면 가장 약한 반격 카드를 내고, 없으면 먹는다.
  - 다음 사람이 1~2장이면 공격 카드를 우선하고, J·Q 로 그 사람 차례를 늦춘다.
  - 평소에는 숫자 카드부터 내고 조커·A 는 방어용으로 아낀다. 7 은 가장 많이 든 무늬로 지정한다.
  - 낼 게 없으면 먹는다.
- **경쟁**: §4.4 의 반응 추첨으로만 참여한다(봇 루프와 무관).
- **`timeoutAction`**(사람 시간 초과): 먹기. 결정적이다.
- 휴리스틱 봇이 무작위 봇보다 우세한지 시뮬레이션으로 확인한다(D-119 방식).
- **실측(S3, D-128, 1,000판·시드 고정)**: 무작위 봇(포트 기본, 합법수 균등) 대비 4인 승률 0.92(기준 0.25),
  1:1 0.96. "낼 수 있으면 늘 내는" 탐욕 봇 3명 대비로도 0.36(기준 0.25, 대조군 0.27) — 규칙 자체가 값을 한다.
  `bot/OneCardBotStrengthTest`.

### 4.7 탈주·파산·종료

- **탈주**(`desert`): 파산과 같은 "탈락" 경로다. 손패는 뽑을 더미 아래로 가고, 차례에서 빠지며,
  순위는 최하위(탈주자끼리 동순위)다. 좌석은 방에 남는다(D-122 좌석 고정과 일치).
- 살아 있는 플레이어가 2명 이상이고 그중 사람이 있으면 `MATCH_CONTINUES`, 아니면 남은 장수로
  순위를 매겨 `MATCH_ENDED`. 같은 판정을 파산 뒤에도 적용한다 — 마지막 사람이 파산해 봇만 남으면
  그 자리에서 끝낸다(봇끼리의 결판을 사람이 기다릴 이유가 없다).
- 창이 열린 동안 탈주하면 창을 벌칙 없이 닫는다(§4.5 불변식).
- 종료 사유: `FINISHED`(다 냄) · `LAST_STANDING`(나머지 전원 탈락) · `STALEMATE`(교착·차례 상한) ·
  `NO_HUMANS`(살아 있는 사람이 없음 — 탈주·파산).
- `supportsRematch()` 는 기본값 false → 정상 종료 시 방이 FINISHED 가 된다. 게임판은 D-120 처럼
  종료 뒤에도 유지해 순위를 보여 준다.

### 4.8 기록·랭킹

- **V12**: `onecard_match_results`(room_id, finished_at, end_reason, payload_json) +
  `onecard_match_participants`(match_id, user_id, seat, final_rank, cards_left, is_win, deserted).
  스컬킹의 2테이블 구조 그대로다.

  인스턴스 간 전파가 아님). D-116 이 먼저 병합되면 그 발행 방식을 따른다.
- 승리는 1등(동순위면 모두 — 교착 종료 등). ELO 는 `EloCalculator.applyFreeForAll` 로, 점수 = `좌석 수 − 순위`, 탈주는

- 랭킹 탭과 전적은 카탈로그 기반이라 자동으로 생긴다(`user_game_stats.game_type = 'ONE_CARD'`).

## 7. 위험과 후속

- **핑 유리**(§4.4 공정성) — 배포 후 로그로 측정한다.
- **봇 반응 구간**이 너무 쉽거나 어려울 수 있다 → 설정값으로 조정하고, 시뮬레이션으로 봇끼리
  잡히는 비율을 본다.
- **3초 창이 템포를 늘어뜨릴 수 있다** → 대부분 첫 누름으로 일찍 닫힌다. 실측 후 창 길이를 조정한다.
- **창 끝 뒤에 처리된 누름**(S2 최종 리뷰 N2): `press` 는 `now` 를 보지 않아 창 끝·봇 추첨 시각 뒤에 처리된 사람
  누름도 이긴다(§9-4 문구는 허용, §9-2·§9-6 의 시간 의미와는 어긋남). 엄격하게 하려면 `press` 에서
  `now >= race.deadline()` 이면 `NO_RACE` — S3 에서 결정한다. **D-128 결정: 인정(현행 유지)** — 서버가 먼저 처리한
  누름이 이긴다. 네트워크 지연에 관대하고, 봇이 추첨 시각보다 최대 한 폴링 주기(250ms) 늦게 누르는 셈이라 반응
  구간 설정에 흡수된다. 배포 후 경쟁 결과 로그로 다시 본다.
- **v1 제외**: 리매치(D-122 후속 "리매치 대기 중 나가면 좌석이 당겨짐"을 먼저 고친 뒤), 내기 칩,
  하우스 룰 옵션(방 옵션으로 변형 선택), 고정 위치 보조 모드.
- **병합 순서**: D-116(다른 세션)이 먼저 main 에 들어가면 기록기 발행 방식은 그것을 따른다.
- **티츄는 카드를 낼 때마다 전원이 resync 한다**(계획 단계 발견, 원카드 범위 밖). 낼 때마다
  비공개 `HAND_DEALT`(D-62)가 순번을 소비해 공개 `TURN_CHANGED` 가 항상 구멍이 된다. 소원 해제처럼
  이벤트가 없는 변화가 이 resync 에 기대고 있어 고치려면 티츄 이벤트를 먼저 보강해야 한다 — 별도 과제.
- **resync 가 잠금 없이 상태와 순번을 따로 읽는다**(모든 게임 공통). 원카드는 결과값 payload 로
  흡수하고(§4.3), 근본 수정(상태 저장과 순번 발급을 한 번에)은 별도 과제로 둔다.
- **D-126 과 겹치는 부분**(2026-10-04 기준 다른 세션에서 진행 중): 티츄 resync 수정이 §4.5b 와 같은
  `GameEvent.sequenced()` 기본 메서드와 "resync 를 방 락 안에서" 읽는 변경을 넣는다. 그쪽이 먼저 병합되면 S3 는
  포트 확장을 새로 만들지 않고 원카드 비공개 이벤트에서 `sequenced()` 를 false 로 재정의만 하며, 위 두 위험
  항목도 그쪽에서 닫힌다. S2 코드는 이 메서드를 쓰지 않으므로 병합 순서와 무관하다.
