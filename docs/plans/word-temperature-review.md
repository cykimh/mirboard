# 새 게임 검토 — 유사도 스무고개(가칭, 방송 게임 계열)
> 2026-11-25 검토(ultracode 워크플로: 분석 4 → 종합 → 반박 비평). 결정 전 초안 — D-번호는 채택 시 D-310 부터.
> **채택(2026-11-25, D-310~D-312)** — 이름 "낱말 온도", 코드 이름 `WORD_TEMP`. 이 문서는 검토 기록으로 남기고(방송의 고유 이름·용어는 저장소에 쓰지 않으려고 "정답 낱말"·"추가 추리권"으로 바꿔 적었다), 정본은 룰 `docs/rules-wordtemp.md`·설계 `docs/plans/wordtemp.md` 다. 아래 "권장 접근"의 "실행 중 LLM 0회·운영비 0원"은 **추가 검토 절과 D-312 로 바뀌었다**(표 + 표 밖만 Claude 실시간 채점).
## 결론
조건부 가능합니다. AI 채점을 '실시간 LLM'에서 '미리 만들어 둔 유사도 표'로 바꾸고 출제자 버티기 구멍만 막으면, 지금 게임 틀에 포트 변경 0건·운영비 0원으로 붙일 수 있습니다. 초안 그대로는 세 군데서 깨집니다. 2초짜리 방 잠금, 무료 원칙, 그리고 판 길이(6인 최악 2시간 반)입니다.

## 핵심 문제와 고칠 점
- **'힌트를 넣자마자 LLM 채점'은 2초짜리 방 잠금 안에서 돌 수 없습니다. `server/src/main/java/com/mirboard/infra/ws/RoomActionLock.java`를 보니 TTL이 2초이고, 액션 경로는 기다리지 않고 BUSY로 거절합니다. LLM 왕복은 0.5~3초이고 실패해서 재시도하면 더 걸립니다. 그러면 잠금이 풀린 채로 상태를 덮어쓰거나, 같은 방의 추리·봇·타이머가 줄줄이 막힙니다. 서버가 나중에 결과를 다시 넣어 줄 길도 없습니다. 들어오는 길은 클라 액션, 봇, 턴 타임아웃, 엔진 타이머 `onTimer`, 탈주뿐입니다.**
  - → 유사도를 미리 계산한 표로 만들어 서버 메모리에서 바로 찾습니다. 별자리 수판의 퍼즐 은행(`server/src/main/resources/starsquare/*.json`, `PuzzleBank` — D-282·D-284)과 같은 방식입니다. 힌트 액션 `apply` 안에서는 표를 한 번 찾기만 하므로 잠금 문제가 없고, 비동기 설계나 포트 확장도 필요 없습니다.
- **무료 원칙과 '같은 쌍은 같은 점수' 보장이 둘 다 깨집니다. 저장소에는 LLM·HTTP 클라이언트가 하나도 없습니다(`server/build.gradle.kts`·`server/src/main` grep 0건). 그래서 '기존 SDK 재사용'은 성립하지 않습니다. gpt-4o-mini는 유료라 카드가 필요합니다. Gemini 무료 등급은 한도가 수시로 줄어 판 도중 멈출 수 있고, 입력이 학습에 쓰일 수 있습니다. 초안의 'Redis 캐시'도 결정성을 지켜 주지 못합니다. 운영 Redis는 저장을 하지 않고(`ops/redis/Dockerfile` `--save '' --appendonly no`, D-171 자동 정지), `maxmemory 200mb noeviction`이라 캐시가 게임 상태 메모리까지 잡아먹습니다.**
  - → 표는 운영자 PC에서 한 번 만들어 저장소에 싣습니다. 실행 중 외부 호출 0회, 비용 0원이고, 재시작·배포 뒤에도 점수가 같습니다. 표에 없는 힌트는 '아직 모르는 낱말이에요'로 거절하고 개수는 깎지 않습니다. 놓친 낱말은 사용자 ID 없이 낱말만 모아 다음 표 갱신 때 넣습니다.
- **출제자 꼼수 하나로 게임이 무너집니다. 아무도 못 맞히면 점수는 출제자가 가져가고, 출제자가 손해 보는 경우는 '힌트 0개'뿐입니다. 그래서 차수마다 엉뚱한 힌트 하나만 내면 위험 없이 1+2+3 = 6점(2라운드는 12점)을 가져갑니다. 방송 규칙의 '관련된 명사만' 조건이 초안에서 빠져서 생긴 구멍입니다.**
  - → 차수별 최저 온도를 둡니다. 공개되는 최고 힌트가 1차 50·2차 60·3차 70 미만이면 그 차수 출제자 점수는 0점이고 진행은 계속됩니다. 수치는 S1 시뮬레이션과 시험판을 보고 조정합니다. 공개 힌트는 온도까지 모두에게 보여 줍니다.
- **판이 너무 깁니다. 힌트 180초를 일찍 끝낼 방법이 없어서 출제자가 거의 매번 다 씁니다. 6인 2라운드면 최악 약 2시간 반, 보통이어도 1시간을 넘습니다. 숨긴 탭은 60분 뒤 끊기는데(D-273) 이 시간과도 겹칩니다.**
  - → [힌트 끝] 버튼을 넣고 힌트는 차수당 최대 5개로 줄입니다. 힌트 90초(60·90·120·180 중 선택), 추리 30초 고정, 모두 내면 바로 마감합니다. 판 길이는 기존 `MATCH_LENGTH`(짧게 = 1라운드)로 고르게 합니다. 이러면 4인 판이 보통 약 20분, 6인 판이 약 30분입니다.
- **방송 고유 이름과 용어를 그대로 씁니다. 방송 게임의 이름에 더해, 블로그 규칙에도 없는 방송의 화폐 용어(추가 추리권)까지 들어왔습니다. 담바둑(D-274)·별자리 수판(D-282)에서 정한 '이름·연출은 새로 짓고, 외부 에셋은 MIT·CC0·CC-BY만'(`docs/plans/wall-magic-games.md` §1.3)과 어긋납니다. 방송 이름의 직역도 쓰면 안 됩니다.**
  - → 새 이름을 짓습니다(결정 1). 추가 추리권은 v1에서 빼고 추리는 차수마다 1개로 합니다. 튜토리얼·화면 문구도 우리 말로 새로 씁니다. 공개 전에 '원작을 몰라도 우리 게임으로 보이나'를 한 번 점검합니다.
- **봇 이야기가 없습니다. 모든 대기실에는 [＋ 봇 추가]와 봇과 연습이 있습니다(D-174·D-290). 그런데 `GameDefinition`에는 '봇 끄기' 선언이 없습니다(직접 확인). 정책이 없으면 기본 `botAction`은 합법 액션 중 하나를 무작위로 고르는데, 힌트·추리는 자유 입력이라 봇이 아무것도 하지 못합니다. 최소 3인이라 친구가 2명뿐이면 봇이 꼭 필요합니다. 분석가 한 명은 '봇 없음'을 권했지만, 그러려면 플랫폼에 봇 끄기 기능을 새로 넣어야 해서 오히려 일이 커집니다.**
  - → 유사도 표가 있으면 봇도 같이 해결됩니다. 출제 봇은 자기 단어의 이웃 중 중간 온도(목표 구간) 단어를 내고, 추리 봇은 공개 힌트로 은행을 거꾸로 찾습니다. 그대로 두면 사람보다 세므로 기존 `BOT_LEVEL` 3단계로 약하게 만듭니다. 정책이 실패하면 ERROR 로그를 남기고 `timeoutAction`으로 넘깁니다(D-118·D-119).
- **숨길 정보와 시간을 어떻게 처리할지 비어 있고, 대기실처럼 플랫폼이 맡는 일까지 게임에 넣었습니다. '출제자에게만 보여 주기'와 '동시 공개'를 어느 경로로 보낼지 없습니다. 한 차례에 힌트를 여러 번 내고 추리는 모두가 동시에 하므로, 액션마다 다시 걸리는 인프라 턴 데드라인으로는 단계를 마감할 수 없습니다. LOBBY 상태와 방장 옵션 3개는 원래 대기실 몫입니다(`RoomService`, D-106·D-176).**
  - → 내 후보·내 단어·출제자 힌트 온도는 `privateView`와 순번 없는 비공개 이벤트로 보냅니다(D-126). '누가 무엇을 보나'는 상태 함수 하나에 모읍니다(별자리 수판 `peerSeats`, D-294). 모든 단계 마감은 상태에 둔 시작 시각과 엔진 타이머 `timer/onTimer`로 처리하고(얏추 D-183, 별자리 수판), `timeoutAction`도 같은 결과를 내게 해서 둘이 겹쳐도 결과가 같게 합니다. LOBBY는 없애고, 시간은 기존 `turnSeconds`를 '힌트 제한'(`turnLimitLabel`, D-286)으로 씁니다.
- **초안의 일반론이 저장소 규약과 반대입니다. 'Socket.IO'라고 썼지만 실제는 STOMP(`/app/room/{id}/action`·`/topic/room/{id}`·`/user/queue/room/{id}`)입니다. '스냅샷 기반'이라고 했지만 실제는 공개 순번 + resync(D-124)입니다. '신규 CSS 금지'도 반대로, 실제 규칙은 새 part + 접두 네임스페이스이고 다음 번호는 29입니다. 게다가 docs 먼저 쓰기, 단계별 승인, Flyway, 공개 스위치 없이 한 번에 다 만들라는 형태입니다.**
  - → 아래 정리한 프롬프트로 바꿉니다. D-310부터 결정을 먼저 쓰고, 룰 정본을 두고, S0~S4 단계마다 승인을 받습니다. Flyway는 V25를 쓰고, `MIRBOARD_<GAME>_STATUS`는 S4 전까지 DISABLED로 둡니다. 완료 조건은 인프라 grep 0건입니다.

## 권장 접근
■ 결론: 유사도는 '미리 만든 표'로 채점하고, 포트 변경 0건, 운영비 0원, v1은 3~6인에 봇 가능, 4인 판 약 20분.

■ AI 엔진(무료만)
- 실행 중에는 LLM을 부르지 않습니다. 운영자 PC에서 표를 한 번 만들어 `server/src/main/resources/<게임>/`에 싣습니다.
- 재료는 두 가지입니다.
  · 정답 낱말 은행 300~600개: 직접 고른, 흔하고 구체적인 명사입니다. 범주와 같은 말 목록(휴대폰=핸드폰)을 함께 둡니다.
  · 힌트 어휘 2~3만 개: 직접 만든 명사 목록입니다. 남의 사전 데이터(우리말샘 CC BY-SA)를 쓰면 라이선스 예외가 필요해서 피하고, 욕설·사람 이름은 뺍니다.
- 만드는 순서
  ① 로컬 임베딩 모델(BGE-M3 또는 multilingual-e5, MIT)로 모든 쌍의 유사도를 내고 후보 순서를 정합니다.
  ② 정답 낱말마다 한 번씩 Claude Code 세션으로 상위 약 200개를 띠(96+ / 75~95 / 40~74 / 그 밖)로 나눕니다. 쌍마다 점수를 매기지 않으므로 약 600번이면 됩니다.
  ③ 띠 안의 순서는 임베딩 값으로 정해 정수 점수로 펼칩니다.
  ④ 운영자와 친구가 무작위 150~200쌍을 검수합니다(띠 일치 80% 이상).
  ⑤ '96+ 이웃 1~5개, 75~95 이웃이 충분한' 단어만 은행에 남깁니다.
- 형식과 부담: 정답 낱말마다 40점 이상 이웃만 점수를 적는 희소형이라 몇 MB이고, 나머지는 낮은 고정값입니다. 서버 힙은 수 MB~20MB 늘어나는데, 한도(512MB×55% ≈ 280MB) 안입니다. 첫 판 때 불러옵니다. Fly 월 사용량은 그대로입니다.
- 장점: 같은 쌍은 늘 같은 점수입니다(표가 정본이고, 표 버전을 매치 상태에 기록). 표에서 찾기만 하므로 프롬프트 주입·욕설 걱정이 없고, 표에 있는지가 곧 '명사인가' 검사입니다.

■ 2초 잠금과의 관계
- 힌트 액션 `apply` 안에서 메모리 조회를 한 번 할 뿐이라 잠금 문제가 없습니다. 비동기 채점이나 폴링 설계가 필요 없습니다.
- 그래도 LLM을 꼭 써야 한다면 길은 하나입니다. 힌트를 '채점 대기'로 저장하고, 잠금 밖에서 채점해 Postgres 캐시에 넣고, 엔진 타이머가 250ms마다 확인해 반영합니다. 복잡하고 한도·비결정 문제가 남아 권하지 않습니다.

■ 포트 확장: 0건
- `GameEngine` 메서드 추가 없음, 새 `RoomOption` 상수 없음.
- 기존 `MATCH_LENGTH`·`BOT_LEVEL`과 `turnLimitLabel`('힌트 제한')을 재사용합니다.
- 인프라에 게임 이름은 0건입니다.

■ v1 룰
- 인원: 3~6인(기본 4), 봇 가능(`BOT_LEVEL` 쉬움·보통·어려움).
- 단어 고르기: 판이 시작되면 각자 후보 3개를 받습니다(서로 다른 범주, 판 전체에서 겹침 없음). 20초 안에 1개를 고르고, 시간이 지나면 무작위로 정합니다. 2라운드는 남은 2개 중에서 고릅니다.
- 출제 순서: 무작위 시작 좌석부터 시계 방향(D-132)으로, 라운드마다 모두 한 번씩 출제합니다.
- 힌트 단계
  · 시간: 90초(60·90·120·180 중 선택). 차수당 최대 5개, 1개 이상 내면 [힌트 끝]을 누를 수 있습니다.
  · 보이는 것: 온도는 출제자에게만 실시간으로 보이고, 다른 사람은 개수('힌트 3/5')만 봅니다.
  · 96점 이상이 나오면 바로 끝나고 그 힌트가 공개됩니다.
- 입력 검증
  · NFC 정규화·공백 제거 뒤 한글 2~10자.
  · 어휘에 있어야 합니다(없으면 거절, 개수는 그대로).
  · 정답 낱말와 서로 포함하면 막습니다(수영↔수영장 양방향).
  · 출제 턴 전체에서 같은 힌트는 다시 못 냅니다.
- 공개: 차수가 끝나면 최고 힌트와 그 온도를 모두에게 보여 주고, 차수가 지나도 쌓아 둡니다.
- 추리
  · 30초 고정, 추리자마다 1개(빈칸 패스 가능). 모두 내면 바로 마감하고 동시에 공개합니다.
  · 정답은 정규화 뒤 완전히 같거나 같은 말 목록에 있을 때만 인정하고, 오답은 단어만 공개합니다.
- 점수
  · 맞힌 사람마다 +1, 그 출제 턴은 끝납니다.
  · 전원 오답이면 출제자가 차수에 따라 +1/+2/+3을 받습니다. 단, 공개 힌트가 50/60/70 미만이면 0점입니다. 3차가 지나면 턴이 끝납니다.
  · 힌트 0개로 시간이 끝나면 출제자 0점, 턴이 끝납니다.
  · 받은 점수는 쌓이고, 2라운드는 모든 점수가 ×2입니다.
- 턴이 끝나면 정답 낱말와 출제자가 낸 힌트 전체·온도를 6초 동안 보여 줍니다.
- 추가 추리권은 없습니다.
- 판 길이(`MATCH_LENGTH`): 짧게 1라운드 / 보통 2라운드(원작) / 길게 3라운드(×3, 후보 3개를 모두 씀).
- 동점은 공동 순위, 모두 같은 점수면 무승부입니다(`recordDraw`).
- 탈주: 판은 계속됩니다(MATCH_CONTINUES). 출제 중에 나가면 그 턴을 0점으로 끝내고, 남은 사람이 2명 미만이면 판을 끝냅니다.

■ 판 길이 추정(보통 = 2라운드)
- 차수 하나는 최악 126초(90+30+6), 보통 약 80초이고, 출제 턴은 평균 약 2차수입니다.

## 비평가 정정
- [표 로딩 시점] 종합안은 표를 '첫 판 때 불러옵니다'라고 했는데, 저장소 관례와 반대이고 위험하기도 합니다. 별자리 수판은 `StarSquarePuzzles`(@Component)의 필드 초기화 `PuzzleBank.fromClasspath()`에서 부팅할 때 읽습니다. 첫 판 때 읽으면 로딩이 매치 시작이나 첫 `apply`에 걸리고, 그 경로는 방 락 2초(`RoomActionLock.TTL`) 안이거나 그 근처입니다. shared-cpu-1x에 C1만 쓰고 SerialGC(`Dockerfile` JAVA_TOOL_OPTIONS)라 수 MB짜리 JSON 파싱이 1초를 넘을 수 있습니다. 부팅할 때 미리 읽고(콜드 스타트는 이미 약 100초 — `fly.toml` 주석), 락 안에서는 조회만 하도록 고쳐야 합니다.
- [메모리 추정] '힙 수 MB~20MB 증가'는 압축 표현일 때만 맞습니다. `Map<String, Map<String,Integer>>`로 담으면 정답 낱말 600개에 40점 이상 이웃 1,000~2,000개씩, 즉 60만~120만 항목이 됩니다. 항목당 약 80~100바이트라 60~120MB가 들어 힙 한도의 절반 가까이를 씁니다. 512MB×55% ≈ 280MB는 최대 힙이지 남는 여유가 아닙니다. 지금 쓰는 양은 재 본 적이 없습니다. 그래서 다음이 필요합니다. (a) 어휘를 int 인덱스로 바꿉니다. (b) 정답 낱말마다 정렬된 `int[]` 이웃과 `byte[]` 점수를 두고 이진 탐색합니다. (c) JSON 대신 압축 바이너리나 줄 단위 형식을 씁니다. (d) S2 완료 조건에 운영 힙 실측(표를 싣기 전후의 사용량)을 넣습니다.
- [‘표 밖 = 낮은 고정값’의 품질 구멍] 종합안은 임베딩 상위 약 200개만 LLM으로 띠를 나누고 나머지는 낮은 고정값을 줍니다. BGE-M3·e5는 문장 임베딩이라 맥락 없는 한국어 낱말 하나에는 약합니다. 반의어와 동음이의어도 높게 나옵니다. 그래서 실제로 가까운 낱말이 201위 밖으로 밀리는 일이 흔하고, 그러면 '빤히 관련 있는데 온도 5' 같은 결과가 나와 게임을 망칩니다. 바로잡을 방향은 이렇습니다. 상위 N개는 LLM 띠로 보정하고, 그 밖의 표에 있는 쌍도 임베딩 값을 띠 경계에 맞춰 단조로 펼친 점수를 적습니다. N은 300~500으로 늘립니다. 고정 저점은 정말 무관한 쌍에만 씁니다.
- [2자 이상 규칙] 초안과 종합안이 모두 '한글 2~10자'를 그대로 쓰는데, 이 규칙은 눈·물·불·별·배·꽃·책·산·차·집 같은 한 글자 핵심 명사를 막습니다(예: 정답 낱말 '바다'에 힌트 '물'). 블로그 규칙은 '한글 명사만'일 뿐 글자 수 제한이 없습니다. 어휘 표가 '명사인가' 검사를 대신하므로 1~10자로 넓히고, 서로 포함 검사(눈↔눈사람)는 그대로 둡니다.
- [어휘 2~3만 '직접 만든 목록'은 비현실적] 2~3만 낱말을 손으로 만들 수는 없습니다. 실제 선택지는 셋이고 출처를 결정 항목으로 올려야 합니다. (3) LLM(Claude)이 범주별로 생성한 명사 목록을 임베딩 모델 어휘와 교차 필터: 출력 권리가 사용자에게 있어 라이선스 면에서 가장 깨끗합니다. 저장소가 PUBLIC(`github.com/cykimh/mirboard`, `gh repo view` 확인)이라 SA 데이터를 싣는 건 실제 배포에 해당합니다. 권장은 (3)이고, CREDITS.md에 생성 방법을 적습니다.
- [추가 추리권 근거] 종합안은 추가 추리권을 '다른 예능에서 쓰는 화폐 이름'이라고 했지만, 담바둑·별자리 수판의 원작과 같은 방송(데블스 플랜 계열로 추정)의 게임 내 화폐일 가능성이 높습니다. 그래서 빼는 이유는 '방송 고유 용어 + 원작의 게임 간 화폐 체계에 기대는 장치'로 적는 것이 정확합니다. 빼자는 결론은 같습니다.
- [DB 원문 비저장 vs 놓친 낱말 수집 모순] 프롬프트 개정안은 '사용자가 친 힌트·답 원문은 DB에 저장하지 않는다'고 하면서 '놓친 낱말을 모아 표를 갱신한다'고 합니다. Fly 로그는 휘발되므로 모으려면 어딘가에 저장해야 합니다. 둘 중 하나로 정해야 합니다. 저장한다면 다음을 지킵니다. 사용자 ID·방 ID 없이 낱말과 횟수만 둡니다(예: V25에 `<game>_missed_words(word PK, count, first_seen)`). 하루·한 판 상한을 둡니다. 어휘 형태(한글 1~10자)를 통과한 것만 받습니다. 어드민에서만 봅니다. 저장하지 않는다면 이 항목을 지웁니다.
- [출제자 점수 누적 해석] 종합안은 '1+2+3 = 6점'으로 누적을 전제했지만, 블로그 요약('1차 +1, 2차 +2, 3차 +3')은 (a) 차수마다 즉시 받아 쌓이는지, (b) 마지막으로 실패한 차수의 점수 하나만 받는지 둘 다로 읽힙니다. (a)라면 2차에 누가 맞혀도 출제자는 1차 점수 1점을 지킵니다. 버티기 구멍의 크기와 최저 온도 설계가 여기에 달려 있어 확인되지 않은 전제를 결론처럼 쓰면 안 됩니다. 결정 항목으로 올려야 합니다.
- [턴 데드라인 재무장 언급 보강] '인프라 턴 데드라인으로는 단계를 마감할 수 없다'는 맞습니다. 다만 더 구체적인 함정이 있습니다. 인프라 데드라인은 액션마다(힌트를 낼 때마다) `turnSeconds`로 다시 걸리고, `pendingSeat`(대기 좌석 중 첫 좌석) 하나에만 `timeoutAction`을 쏩니다. 그래서 `timeoutAction`이 '힌트 단계 끝'을 그대로 수행하면 출제자가 힌트를 낼 때마다 마감이 밀린 시각에 한 번 더 발화합니다. 그때는 이미 다음 단계(추리·공개)일 수 있습니다. 그러므로 `timeoutAction`은 지금 단계와 지금 차수를 확인한 뒤에만 동작하는 멱등 액션이어야 하고, 실제 마감은 엔진 타이머만 맡아야 합니다(얏추 D-183의 방식과 같습니다).
- [‘들어오는 길’ 목록] 상태를 바꾸는 진입점에는 클라 액션·봇·턴 타임아웃·`onTimer`·탈주 외에 방장 강퇴(`HostKickService` → `processDesertion`, D-162)와 강제 종료(`GameAbortService`)도 있습니다. 출제 중 강퇴도 '출제 중 탈주'와 같은 갈래로 시험해야 합니다.

## 비평가 추가 위험
- [공개 저장소 = 정답 은행 공개] 저장소가 PUBLIC이라 `server/src/main/resources/<게임>/`의 정답 낱말 은행(300~600개)과 유사도 표를 누구나 내려받을 수 있습니다. 공개된 '최고 힌트 + 온도'로 표를 거꾸로 찾으면 후보가 몇 개로 좁혀져 사람이 스크립트로 이길 수 있습니다. 친구끼리라 위험은 낮지만 결정은 필요합니다. 선택지는 세 가지입니다. (a) 감수합니다(공지만). (b) 은행과 표를 비공개 저장소나 Fly 볼륨에 두고 빌드 때 주입합니다(무료이지만 재현 문서가 필요). (c) 표는 공개하고 은행만 비밀로 둡니다. 쇼케이스 문서의 '재현 명령' 원칙(CLAUDE.md D-105)과도 부딪치므로 S0에서 정해야 합니다.
- [어려움 봇이 사람보다 압도적으로 셈] 추리 봇이 '은행을 거꾸로 찾기'를 하면 닫힌 집합(은행 전체)과 정확한 표를 함께 압니다. 그러면 공개 힌트 1개와 온도만으로 거의 확정할 수 있는데, 사람은 은행을 모릅니다. D-118의 '공개 정보만' 원칙에 형식상 어긋나지는 않지만 실질적으로는 정보 우위입니다. 그래서 BOT_LEVEL마다 다음을 명시해야 합니다. 은행 일부만 앎, 온도에 잡음 섞기, 맞힐 확률 상한(예: 쉬움 15%, 보통 35%, 어려움 55%). 기존 봇 평가처럼 `MIRBOARD_BOT_EVAL` 표로 강도를 재는 일도 S2 완료 조건에 넣어야 합니다.
- [추리 정답 판정 규칙] 완전 일치와 같은 말 목록 말고도 정할 것이 남아 있습니다. 외래어 표기 변형(케이크/케잌, 컴퓨터/컴퓨타), 조사·어미를 붙인 답('사과요', '사과다'), 띄어쓰기('아이스 크림'), 한 글자 차이 오타입니다. 하나라도 인정하면 출제자가 손해를 보고, 하나도 인정하지 않으면 추리자가 억울합니다. 권장안은 이렇습니다. 정규화(NFC·공백·문장부호 제거, 끝 조사 몇 개 제거) + 같은 말·표기 변형 목록만 인정하고 오타는 불인정합니다. 경계 사례 표를 룰 정본에 싣고 테스트로 고정합니다.
- [동음이의어] 배(과일·배·신체), 눈(눈알·눈송이), 다리, 차, 말 같은 낱말은 정답 낱말든 힌트든 온도가 엉뚱해지는 주원인입니다. 정답 낱말 은행에는 뜻이 하나인 낱말만 넣거나 뜻 주석을 달아야 합니다(정답은 표기로 판정). 힌트 쪽은 여러 뜻 중 가장 높은 온도를 쓴다고 정합니다. LLM으로 띠를 나눌 때도 '정답 낱말의 뜻 = 주석의 뜻'을 프롬프트에 고정합니다.
- [공개되는 추리 답의 욕설] 힌트는 어휘 표로 걸러지지만 추리 답은 자유 입력이라 차례가 끝나면 모두에게 공개됩니다. 선택지는 둘입니다. (a) 추리 답도 어휘 표나 금칙어로 거르고 걸리면 '***'로 공개합니다. (b) 오답은 본인에게만 보이고 남에게는 '오답'만 보입니다. 방 채팅이 이미 필터 없이 열려 있어(`RoomChatController`, 신고는 `ChatReportService`) 엄격할 필요는 없지만 결정은 해야 합니다.
- [출제자가 추리를 미리 보는 경로 차단] 다음을 명시해야 합니다. 추리 단계 중 제출 내용은 공개 토픽·공개 뷰·출제자 `privateView` 어디에도 없어야 하고, 공개 이벤트는 '좌석 N 제출함'(내용 없음)만 냅니다. 추리자끼리도 동시 공개 전에는 남의 답을 보지 못합니다. 늦게 들어온 resync나 관전자 입장에도 답이 없어야 합니다. 제출 내용은 본인 큐(순번 없음)로만 '내가 낸 답'을 되돌립니다. 판정 함수 하나(예: `visibleGuesses(state, viewerSeat)`)로 모으고, '공개 뷰 JSON에 답 문자열이 없음'을 직렬화 테스트로 검사합니다(별자리 수판 D-294와 같은 방식).
- [아직 쓰지 않은 후보 단어 은닉] 2라운드(그리고 '길게' 3라운드)에 쓸 남은 후보는 차례가 끝날 때나 라운드가 끝날 때 공개하면 안 됩니다. 매치가 끝날 때까지 본인 `privateView`에만 둡니다. 차례가 끝날 때의 공개는 '이번 정답 낱말 + 그 차례의 힌트·온도'로 한정합니다. 공개 결과 요약(MATCH_ENDED)에 후보 전체를 실을지도 정해야 합니다.
- [관전자·채팅·좌석 위 채팅 줄 누설] 방 채팅은 참가자와 관전자 모두에게 열려 있습니다(`/topic/room/{id}/chat`, `docs/stomp-protocol.md`). 출제자가 채팅에 정답을 치거나 관전자가 정답을 흘리는 일은 기술로 막지 않습니다(막으려면 인프라 변경이 필요해 포트 0건 원칙과 충돌). 이 점을 룰 문서에 '사회적 규칙'으로 명시하고, 튜토리얼에 '채팅으로 알려 주기 금지'를 한 줄 넣습니다. 관전자는 공개 정보만 받고(D-294와 같은 기준), 출제자 온도는 받지 않습니다.
- [배포 중 표 버전 바뀜] Redis 상태는 앱 재배포 뒤에도 남으므로(Redis는 별도 머신), 진행 중인 판이 새 표 버전으로 이어질 수 있습니다. '표 버전을 매치 상태에 기록'만으로는 부족하고, 버전이 다를 때의 동작을 정해야 합니다. 선택지는 직전 버전 표를 하나 더 들고 있기, 그 판을 무승부로 끝내기, 그대로 진행하고 기록만 남기기 중 하나입니다.
- [출제 봇의 속도와 연출] 봇 출제자가 힌트 5개를 0초에 다 내면 재미가 없습니다. 힌트 사이에 3~8초 간격을 두는데, 이 간격은 기존 봇 스케줄러 지연을 쓸지 엔진 타이머로 둘지 정해야 합니다. 추리 봇도 즉시 내면 '모두 내면 바로 마감' 때문에 사람이 압박을 받으니 무작위 지연을 둡니다.
- [1글자 힌트를 허용할 때의 포함 검사] 1~10자로 넓히면 서로 포함 검사가 너무 넓어집니다(정답 낱말 '눈사람'에 '사람'·'눈' 둘 다 막힘). '완전 일치 + 정답 낱말를 포함하는 힌트만 막기 + 같은 말 목록 막기'와 '양방향' 중에서 정해야 합니다. 같은 말 목록(휴대폰↔핸드폰)을 힌트 금지에 넣는 것도 빠져 있습니다.
- [LLM 띠 분류 작업량과 '무료'의 의미] 정답 낱말 약 600개 × 상위 200~500개를 Claude Code로 분류하는 일은 운영자 구독 한도를 씁니다(추가 과금은 0원이지만 시간과 한도는 듭니다). 한 번에 정답 낱말 5~10개씩 묶는 배치, 중간 저장, 같은 입력이면 다시 묻지 않는 캐시를 `scripts/<게임>-data`에 넣어야 하루 안에 끝납니다. 임베딩 모델(BGE-M3 약 2GB)은 운영자 PC에서만 돌리고 저장소에는 결과만 싣는다는 점도 명시합니다.
- [휴대폰 한글 입력] 힌트·추리 입력란은 IME 조합 중 Enter(`compositionend` 전)로 반쪽 글자가 나가는 문제를 막아야 합니다. iOS에서 NFD가 들어올 수 있으니 서버는 NFC로 정규화합니다. 게임판 글자 선택 막기(D-292) 예외를 입력란에 적용하고, 30초 추리 동안 키보드가 판을 가리는 휴대폰 화면 배치(375×812 e2e)도 S3 완료 조건에 넣습니다.
- [동점·무승부와 레이팅] `EloCalculator.Placement(player, score, deserted)`는 점수 기반이라 공동 순위를 표현할 수 있습니다. 다만 '모두 같은 점수 = `recordDraw`' 말고 '일부만 동점'을 `freeForAllDeltas`가 어떻게 처리하는지 기록기 테스트에 넣어야 합니다. 판이 짧은 '짧게'(1라운드)에도 참가 점수(D-301 +6/+2)를 그대로 줄지도 정해야 합니다.

## 2. 유사도(무료·결정적)
- 실행 중 LLM은 쓰지 않는다. 오프라인 도구가 만든 자원을 server/src/main/resources/<게임>/에 둔다.
  - 정답 낱말 은행 300~600개(범주·같은 말 목록 포함).
  - 힌트 어휘 2~3만 명사(직접 만든 목록).
  - 희소 유사도 표: 정답 낱말별 40점 이상 이웃만 점수, 나머지는 낮은 고정값.
  - 표 버전.
- 만드는 법: 로컬 임베딩(MIT)으로 후보 → 정답 낱말당 1회 띠 분류(96+/75~95/40~74/그 밖) → 띠 안을 단조 정수화 → 표본 검수.
- 자원이 정본이고, 도구는 재현 기록으로 저장소에 둔다. 형태 검증 테스트를 붙인다.
- 엔진은 SimilarityTable 인터페이스만 본다(테스트는 작은 고정 표). apply 안에서 O(1)로 조회한다.

## 3. 룰 v1 (판정은 전부 엔진)
- 단계: WORD_SELECT(20초) → HINT(힌트 제한) → GUESS(30초) → REVEAL(6초) → … → ROUND_END → MATCH_ENDED.
- 마감: 모든 단계를 상태에 둔 시작 시각 + 엔진 타이머 timer/onTimer로 마감한다. pendingSeats는 단계별로 정하고, timeoutAction은 같은 결과를 낸다.
- 단어 고르기: 후보 3개(서로 다른 범주, 판 전체 겹침 없음) 중 1개. 시간이 지나면 무작위. 2라운드는 남은 2개 중에서.
- 출제 순서: 무작위 시작 좌석부터 시계 방향.
- 힌트
  - 차수당 최대 5개, [힌트 끝](1개 이상일 때), 96 이상이면 즉시 공개.
  - 검증: NFC·공백 제거 뒤 한글 2~10자 / 어휘에 있어야 함(없으면 거절, 개수 그대로) / 정답 낱말와 양방향 포함 금지 / 출제 턴 전체 중복 금지 / 금칙어.
- 공개: 차수 끝에 최고 힌트+온도(누적). 진행 중에는 개수만. 온도와 출제자 힌트 목록은 출제자 본인 큐로만.
- 추리: 차수마다 1개(패스 가능), 모두 내면 즉시 마감, 동시 공개. 정답은 정규화 뒤 완전 일치 + 같은 말 목록.
- 점수
  - 맞힌 사람 +1, 턴 끝.
  - 전원 오답이면 출제자 +1/+2/+3. 단, 공개 힌트가 50/60/70 미만이면 0점.
  - 힌트 0개면 출제자 0점, 턴 끝.
  - 2라운드 ×2(길게 = 3라운드 ×3). 추가 추리권 없음.
- 순위: 동점은 공동 순위, 모두 같으면 무승부.
- 탈주: MATCH_CONTINUES. 출제 중 탈주는 그 턴을 끝내고, 활성 좌석이 2명 미만이면 판을 끝낸다.
- 은닉
  - '누가 무엇을 보나'는 상태 함수 하나로 정한다.
  - 공개 뷰 타입에는 비밀 필드를 두지 않는다.
  - 관전자·봇·탈주 좌석에는 비공개 정보를 보내지 않는다.
  - MATCH_ENDED에는 요약만 싣는다.
- 봇: 출제는 자기 단어 이웃 중 목표 온도대, 추리는 공개 힌트로 은행을 거꾸로 찾기. BOT_LEVEL로 약하게 하고, 예외가 나면 timeoutAction으로 넘긴다.

## 4. 단계
S0 룰·결정 → S1 데이터·순수 엔진·시뮬레이션(판 길이·점수 분포) → S2 어댑터·봇·기록 → S3 클라(디자인·소리 Fable 5.2) → S4 시험판·공개. 공개 전까지 STATUS=DISABLED.


## 추가 검토 (2026-11-25) — Claude API(크레딧) 채점

사용자 결정: 이름 "낱말 온도", 출제자 점수는 차수마다 쌓기 + 차수별 최저 온도, 3~6인·봇 가능·힌트 90초. AI 채점은 "Claude API 크레딧으로 가능한지" 검토.

- **가능.** 서버(Java)에 공식 Anthropic Java SDK를 붙이고 구조화 출력(`output_config.format`, JSON 스키마 `{isValidNoun, similarityScore, reason}`)으로 받는다. 키는 Fly secrets `ANTHROPIC_API_KEY`. 단어만 보내고 사용자 정보는 보내지 않는다.
- **2초 방 잠금은 그대로 문제** — 실시간 호출은 1~5초라 apply 안에서 못 부른다. 힌트를 '채점 중'으로 저장 → 잠금 밖에서 호출 → 결과를 Postgres 캐시에 저장 → 엔진 타이머(250ms)가 반영하는 비동기 길이 필요(종합안 B안).
- **결정성** — 최신 모델은 temperature 를 받지 않아 같은 쌍도 매번 조금 다를 수 있다. 처음 받은 점수를 Postgres(모델·프롬프트 버전 포함 키)에 저장하고 판 상태에도 확정 점수를 둔다. 운영 Redis 는 저장하지 않으므로 캐시로 부적합.
- **추천: 하이브리드** — 표는 Claude Batch(50% 할인)로 한 번 미리 만들고(대부분 즉시·봇 가능), 표에 없는 힌트만 실시간 Claude 호출.
- **비용 추정**(4인·월 40판 ≈ 힌트 3,200개, 호출당 입력 ~700·출력 ~300 토큰 가정 — 실측 필요):

| 모델 | 실시간만(월) | 하이브리드: 표 1회 + 실시간 ~30%(월) |
|---|---|---|
| Opus 5.5 ($4/$20) | 약 $29 | 표 약 $20~40 + 월 약 $9 |
| Sonnet 5.5 ($2/$10) | 약 $14 | 표 약 $10~20 + 월 약 $4 |
| Haiku 5.5 ($0.10/$0.50) | 약 $0.6 | 표 약 $1 + 월 약 $0.2 |

- 안전장치: 하루 호출 상한·킬스위치(설정 한 줄), Console 지출 한도, 실패·시간 초과 시 그 힌트 무효(개수 반환).
