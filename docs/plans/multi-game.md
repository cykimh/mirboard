> 트랙: M5 / T7 (`parallel-tracks.md`). 착수 시 `docs/decisions.md` 에 D-NN 선행.
> 원자료: 볼트 `inbox/clippings/{스컬킹,요트(주사위),할리갈리}.md` (나무위키 클리핑)

## 1. 먼저 알아야 할 것 — "Bean 만 추가하면 된다"는 지금 사실이 아니다

`CLAUDE.md` 와 D-06/D-11 은 "새 게임 = `domain.game.{newgame}` 패키지 + `GameDefinition`
Bean 등록 → 카탈로그/방 생성/엔진 디스패치가 자동 연결"이라고 못 박고 있다. **카탈로그까지는
사실이지만 인게임은 아니다.** 실측 결과:

| 확인 항목 | 실제 |
| --- | --- |
| `GameEngine` 인터페이스 | **메서드 0개** (빈 마커) |
| `GameAction` / `GameEvent` | **메서드 0개** (빈 마커) |
| `GameDefinition.newEngine()` | **호출부 0건** — 정의만 있고 죽은 코드 |
| infra 의 Tichu 직접 참조 | **10개 파일 · 123회** |

참조가 몰린 곳 (많은 순): `BotScheduler`(24) · `TurnTimeoutScheduler`(22) ·
`MatchProgressService`(21) · `GameStompController`(20) · `RoomController`(14) ·
`DesertionService`(11) · `GameEventBroadcaster`(6) · `RoomChipService`(4).

`GameStompController` 는 `@Payload TichuAction` 으로 **타입까지 Tichu 로 고정**돼 있고,
엔진도 `new TichuEngine(...)` 로 직접 생성한다. 즉 **두 번째 게임을 넣으려면 포트를 먼저
만들어야 한다** — 이게 로드맵이 M5 를 "GameEngine 포트 졸업"이라 부른 이유다.

> 문서와 코드가 어긋나 있다. 착수 시 CLAUDE.md 의 "새 게임 추가 절차" 문구를 현재
> 상태에 맞게 고치거나(권장), 포트를 만들어 문구를 참으로 만든다.

## 2. 세 게임의 형태 — 난이도가 전혀 다르다

현재 플랫폼의 전제는 **턴제 · 4인 고정 · 손패 은닉 · 트릭**이다. 세 게임을 그 축에 놓으면:

| 축 | 티츄 (현재) | 스컬킹 | 요트 | 할리갈리 |
| --- | --- | --- | --- | --- |
| 턴제인가 | ✅ | ✅ | ✅ | ❌ **실시간** |
| 인원 | 4 고정 | 가변(2~6·8) | 가변(1~N) | 가변(2~6) |
| 비공개 상태 | 손패 | 손패 | **없음**(점수판 공개) | 자기 덱도 안 봄 |
| 트릭/리드수트 | ✅ | ✅ | ❌ | ❌ |
| 라운드 구조 | 가변(1000점까지) | **정확히 10** | **정확히 12**(족보 수) | 탈락제 |
| 턴 내 무작위 | ❌ | ❌ | ✅ **주사위 3회** | ❌ |
| 플레이어 상호작용 | 높음 | 높음 | **거의 없음** | 높음(경쟁) |
| 팀 | 2:2 고정 | 개인전 | 개인전 | 개인전 |

**세 게임이 요구하는 변경이 서로 다르다.** 하나씩 보면:

### 스컬킹 — 재사용률 최고, 포트 검증에 최적
트릭테이킹이라 티츄와 뼈대를 공유한다: 손패 분배 · 리드 수트 · 트릭 승자 판정 · 라운드 점수 ·
특수 카드 우선순위. 다른 점은 **입찰(예측) 단계**가 라운드마다 들어가고, 라운드 N 에 N 장을
나누며(1→10장), 점수가 "예측 적중" 기반이라는 것.

특수 카드 상호작용은 티츄의 Phoenix/Dragon 만큼 까다롭다 — 해적 > 색상, 스컬킹 > 해적,
인어 > 스컬킹의 **비추이적 삼각관계**, 티그리스(해적/탈출 선언 선택), 동일 카드 복수 시
"먼저 낸 사람" 판정. `HandComparator` 를 일반화할 좋은 시험대다.

### 요트 — 포트가 진짜 일반적인지 시험하는 리트머스
턴제지만 티츄와 공유하는 게 거의 없다. **비공개 상태가 아예 없고**(점수판이 공개),
트릭도 손패도 없다. 대신 새로 필요한 것: **턴 내부 상태 머신**(굴림 1→2→3, 주사위 고정/재굴림),
**서버 측 난수**(주사위 — 셔플과 같은 이유로 서버 권위 필수), 12칸 점수판.

플레이어 상호작용이 없어서 "차례를 기다리는 시간"이 UX 문제가 된다(4인이면 내 턴은 25%).
동시 진행 허용 여부는 룰이 아니라 **제품 결정**이다.

### 할리갈리 — 플랫폼 전제를 깬다. 별도 결정 필요
카드를 뒤집는 것만 턴제이고 **종 치기는 전원 동시 경쟁**이다. 이건 규칙 구현 난이도가 아니라
**아키텍처 전제의 문제**다:

- `RoomActionLock`(SET NX EX 2s)은 "한 번에 한 액션"을 보장할 뿐, **누가 먼저였는지**를
  판정하지 않는다. 실시간 경쟁은 밀리초 순서가 곧 승패다.
- `TurnTimeoutScheduler`·`currentTurnSeat` 모델이 통째로 무의미하다.
- **네트워크 지연이 승패를 결정한다.** 오프라인 할리갈리는 반사신경 게임이지만, 온라인에서는
  핑이 낮은 사람이 이긴다. 서버 도착 순서로 판정할지, 클라 타임스탬프를 신뢰할지(치팅 노출),
  보정을 넣을지는 **게임 디자인 결정**이지 구현 세부가 아니다.
- 지금 서사가 "서버-권위적 실시간 게임 서버"라 오히려 쇼케이스 가치는 높다. 다만 **M5 가
  아니라 별도 마일스톤**으로 다뤄야 할 규모다.

## 3. 권고

**셋을 한 번에 하지 마라. 순서는 스컬킹 → 요트 → (별도 결정) 할리갈리.**

이유는 각 게임이 **포트 설계에 던지는 질문이 다르기 때문**이다.

1. **스컬킹으로 포트를 졸업시킨다.** 티츄와 같은 계열이라 "포트가 두 트릭테이킹 게임을
   담을 수 있는가"를 검증한다. 여기서 포트가 티츄 모양으로 굳으면 실패다 — 그래서 2번이 필요하다.
2. **요트로 포트가 진짜 일반적인지 시험한다.** 손패도 트릭도 없는 게임이 같은 포트에
   들어가면 추상화가 진짜다. 안 들어가면 그때 고친다 — 포트는 두 번째 사례가 아니라 **세 번째
   사례에서 검증된다**.
3. **할리갈리는 실시간 결정을 먼저 한다.** 규칙 구현이 아니라 판정 모델(도착 순서 vs 클라
   타임스탬프 vs 보정)과 공정성 정책을 정해야 착수할 수 있다.

## 4. 선행 조건 (협상 불가)

`parallel-tracks.md` 의 순서 제약이 그대로 적용된다: **M3(수평확장) → M5(멀티게임)**.

M3 는 `TurnTimeoutScheduler`/`BotScheduler` 를 Redis 기반으로 **분산 재작성**하고,
M5 는 **같은 파일을 포트화**한다. 전면 재작성 2건이 같은 파일에 겹치므로 M3 가 먼저다.
순서를 뒤집으면 포트화한 것을 M3 가 다시 갈아엎는다.

또한 T5 2차(`tichuStore` 분리)가 M5 의 클라 작업과 겹친다 — 클라는 동시 1트랙이다.

## 5. 단계 계획

### 0단계 — 결정 (코드 0)
아래 §7 의 열린 질문에 답한다. 특히 인원 가변 정책과 할리갈리 판정 모델.

### 1단계 — 포트 설계 (코드 0, 문서만)
현재 `TichuEngine`/`GameStompController`/`MatchProgressService` 가 실제로 하는 일을 열거해
**포트 표면**을 확정한다. 지금 티츄가 요구하는 최소 표면은 대략:

| 포트 | 책임 | 요트가 깨는 지점 |
| --- | --- | --- |
| `apply(state, seat, action) → (newState, events)` | 룰 적용 | — |
| 상태 직렬화(JSON) | Redis 영속 | — |
| 공개 뷰 / 비공개 뷰 | State Hiding | **비공개 뷰가 없다** → Optional |
| 단계(phase) 이름 | 클라 분기 | 단계 집합이 게임마다 다름 |
| 라운드/매치 진행 판정 | 종료·다음 라운드 | 티츄는 점수, 스컬킹은 10라운드, 요트는 12칸 |
| 합법 액션 열거 | 봇 | 요트는 조합 폭발(주사위 고정 2^5 × 12칸) |
| 타임아웃 기본 액션 | 자동 진행 | — |

**산출물**: `docs/game-port.md` + D-NN. 코드는 아직 안 건드린다.

### 2단계 — 포트 추출 (동작 무변경)
티츄를 포트 뒤로 옮긴다. **게임은 하나 그대로**이므로 D-87 과 같은 "동작 무변경 리팩토링"이고,
기존 테스트 전량(서버 383건)이 안전망이다. `newEngine()` 을 되살려 실제 디스패치에 쓴다.

- `GameStompController` 에서 `TichuAction` 하드타입 제거 → 게임별 액션 역직렬화 seam
- `MatchProgressService`·`BotScheduler`·`TurnTimeoutScheduler` 를 포트 뒤로
- **검증**: 티츄 회귀 383건 + `bot-stress` + 라이브 풀매치

### 3단계 — 인원 가변 지원 (플랫폼 변경)
현재 `Room.capacity = definition.maxPlayers()` 로 **고정**이다. 스컬킹(2~6)·요트(1~N)는
방 생성 시 인원을 고르게 해야 한다. `POST /api/rooms` 계약 변경 + 클라 모달 + docs.
→ 계약 슬라이스이므로 서버 DTO + 클라 미러 + docs 한 커밋(직렬화 지점 4).

### 4단계 — 스컬킹 구현
`domain.game.skullking` 신설. 티츄와 같은 순서로: 카드/덱 → 트릭 판정(비추이적 삼각관계) →
입찰 단계 → 점수 → 엔진 통합 → 봇 → 클라.
**규칙 명세를 먼저 쓴다**(`docs/rules-skullking.md`) — D-56(`rules-tichu.md`)이 룰 코드
1:1 매핑의 단일 진실원으로 잘 작동한 선례.

### 5단계 — 요트 구현 (포트 검증)
`domain.game.yacht`. 여기서 **포트를 고쳐야 하면 그게 정상**이다 — 2단계 포트가 티츄
모양으로 굳었다는 신호이므로 고치고 스컬킹 회귀로 확인한다.

### 6단계 — 할리갈리 (별도 마일스톤)
0단계 결정이 끝난 뒤 재평가. 실시간 판정·공정성·부정 방지가 본체이고 규칙은 곁다리다.

## 6. 범위 밖 (이번에 하지 않는 것)

- **티츄 룰 변경** — 포트 추출은 동작 무변경이다.
- **D-82 칩/내기의 다게임 확장** — 칩은 현재 티츄 매치 종료에 묶여 있다. 다게임 정산은
  별건이고, 우선 신규 게임은 `stake=0` 으로 시작한다.
- **ELO 의 게임별 분리** — 현재 `users.rating` 단일 컬럼이다. 게임마다 레이팅을 나누려면
  스키마 변경(D-02 화이트리스트 검토 필요)이라 별도 결정.
- **나무위키 원문의 상급자 룰 전량** — 스컬킹 약탈/크라켄/흰고래 등은 기본 룰 안정화 후.

## 7. 열린 질문 (사용자 결정 필요)

1. **어느 게임을 먼저?** 위 권고는 스컬킹이지만, "요트가 더 만만해 보인다"면 순서를 바꿀 수
   있다. 다만 요트를 먼저 하면 포트가 "손패 없는 게임" 쪽으로 치우친다.
2. **인원 가변을 3단계에서 할 것인가, 신규 게임도 인원 고정으로 시작할 것인가?**
   고정(예: 스컬킹 4인 전용)으로 시작하면 3단계를 건너뛰고 빨리 굴려볼 수 있다.
3. **할리갈리 판정 모델** — 서버 도착 순서(공정하지만 핑 유리) / 클라 타임스탬프(치팅 노출) /
   보정. 이게 정해져야 착수 가능하다.
4. **요트의 턴 대기 UX** — 4인이면 내 턴이 25%다. 순차 진행 / 동시 진행 / 인원 상한 축소 중 선택.
5. **M3 를 먼저 할 것인가?** 순서 제약상 M5 앞에 M3 가 와야 한다. M3 를 건너뛰고 M5 를 하면
   M3 때 포트를 다시 갈아엎게 된다 — 그래도 게임을 먼저 늘리고 싶다면 그 비용을 감수하는 결정이 필요하다.
